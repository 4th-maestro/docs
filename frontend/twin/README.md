# 제6공학관 디지털 트윈 — 데이터 → 렌더링

이 화면은 **데이터를 받아서 그리기만** 합니다. 건물 형상, 설비, 상태 값은 화면 코드에 들어 있지 않고, 모두 아래 데이터에서 나옵니다.
쓰는 데이터는 **회사가 보유한 자료 형식**과 **회사·학생 모두 접근할 수 있는 공공 데이터**뿐입니다.

## 실행

`start-twin.bat`을 더블클릭하면 로컬 서버가 뜨고 브라우저가 열립니다.
직접 실행하려면 아래 명령을 쓰면 됩니다. 그다음 `http://localhost:8766/digital-twin.html`을 엽니다.

```
node tools/sim-server.mjs 8766
```

- 이 서버는 화면 파일을 보여 주고, 시뮬레이션 계산(EnergyPlus)도 맡습니다. 이 컴퓨터(127.0.0.1)에서만 열립니다.
- `python -m http.server 8766`로도 화면은 열립니다. 다만 이 경우 시뮬레이션은 저장된 `scenario.json`만 보여 줍니다.

## 화면 디자인과 테마

- 색, 글꼴(SUIT Variable), 라운드, 그림자, 버튼 크기는 앱 `src/index.css` 토큰과 같은 값입니다. 기준은 작업 공간 `DESIGN.md`(운영자 화면 기준)와 디자인 시스템 6절입니다.
- 히트맵 색은 앱 `src/heat.ts`와 같은 5단계입니다. 범위는 온도 16~28℃, 전력 0~6kW, 습도 30~70%이고, 범위 밖 값은 양끝 색으로 표시합니다.
- 테마는 주소 `theme=light|dark`와 부모 창 메시지 `{source:'maestro', type:'theme', theme}`로 적용합니다. 둘 다 없으면 시스템 설정을 따릅니다. `digital-twin.html`과 `pipeline.html` 모두 같습니다.
- 아이콘은 lucide 1.76.0(앱 `lucide-react`와 같은 판) 경로를 인라인 SVG로 씁니다. 이모지와 기호 문자는 쓰지 않습니다.

## 입력 데이터 (data/)

| 파일 | 구분 | 실제 출처 | schema |
|---|---|---|---|
| `building.json` | 회사 | 설계·시공 도면 + 설비대장 (실 형상·용도·정원, 실내기 위치·모델·계통) | `twin.building/v1` |
| 실시간 스트림 | 회사 | LG 중앙제어기 · BMS (실내기 ON/OFF·설정·흡입 온습도·풍량·에러, 전력 계측) | `twin.realtime/v1` |
| `maintenance.json` | 회사 | 유지보수·서비스 이력 (누적 운전시간, 필터 청소, 과거 고장) | `twin.maintenance/v1` |
| `schedule.json` | 공공 | 부산대 학사 시간표 (수강편람: 강의실·시간·수강 인원) | `twin.schedule/v1` |
| `weather.json` | 공공 | 기상청 단기예보 조회서비스 응답 그대로 | `kma.getVilageFcst` |
| `tariff.json` | 공공 | 한전 전기요금표 (교육용) | `twin.tariff/v1` |

실시간 데이터의 형식 예시는 `data/realtime.sample.json`에 있습니다.

**현재 값의 상태**

- `building.json`: 아래 **자료 → 트윈 파이프라인**이 평면도 사진에서 만든 결과입니다 (`node tools/run-pipeline.mjs`).
- 나머지: 형식만 실제와 같고 값은 가상입니다. `tools/make-virtual-data.mjs`로 다시 만들 수 있습니다.
- Wi-Fi 접속 수처럼 회사도 공공도 아닌 데이터는 쓰지 않습니다. 재실 인원은 **학사 시간표의 수강 인원**만으로 판단합니다.

## 자료 → 트윈 파이프라인 (building.json 만들기)

현장에서 받을 수 있는 자료(평면도, 내부·외부 사진, 에어컨 사진)만으로 building.json을 만듭니다. 브라우저에서 `pipeline.html`을 열면 됩니다.

| 단계 | 넣는 자료 | 자동으로 하는 일 | 사람이 하는 일 |
|---|---|---|---|
| 1 건물 정보 | 건축물대장 | — | 크기·층고·천장고 입력 |
| 2 평면도 | 피난안내도 사진, 와이파이맵, CAD 캡처 | 원근 보정 → 벽 검출 → 공간 분할 → 다각형 | 모서리 4점, 호실·용도·정원 라벨, 가린 벽 긋기 |
| 3 외부 사진 | 입면 사진 | 창 높이 = 비율 × 층고 | 슬래브 선, 창 위·아래 선 클릭 |
| 4 내부 사진 | 강의실 사진 | 바닥·벽 색 (영역 중앙값) | 바닥·벽 영역 드래그, 방 또는 용도 지정 |
| 5 에어컨 사진 | 천장 사진 | 용량 선정, 방 안 배치, 실외기 계통 | 실내기 하나씩 클릭 |
| 6 결과 | — | building.json, 반복 실행 검증 | 트윈에서 확인 |

- 사람이 한 입력은 모두 **레시피**(`source/eng6/recipe.json`)에 남습니다. 같은 이미지와 같은 레시피를 넣으면 항상 같은 building.json이 나옵니다. 브라우저와 명령줄의 결과 해시도 같습니다.
- 에어컨 사진이 없는 방은 면적 40㎡당 1대로 추정합니다. 이 경우 실내기마다 `basis`에 "추정"이라고 적힙니다.
- 가구는 그리지 않습니다.
- 명령줄로 실행하려면 `node tools/run-pipeline.mjs source/eng6/recipe.json data/building.json`을 씁니다. 그다음 `node tools/make-virtual-data.mjs`로 가상 데이터를 다시 만듭니다.

**원본 이미지 보관**

- `source/*/photos/`, `source/*/plans/`의 사진·안내도와 `data/**/skyview.png`는 저장소에 포함하지 않습니다(2026-11-20 결정). 출처와 사용 조건을 확인하지 못했습니다.
- 레시피를 다시 실행하려면 원본 이미지를 같은 경로에 넣으십시오. 원본은 PR #11의 첫 커밋(`7401f98`)에 있습니다. 예: `git show 7401f98:twin/source/eng6/photos/interior-1.jpg > twin/source/eng6/photos/interior-1.jpg`
- 이미지 출처(직접 촬영, 기관 게시물 등)와 사용 조건은 작성자 확인 후 이 절에 기록하십시오.

**제6공학관 예시** (`source/eng6/`)

- 2·3층: 피난안내도 사진에서 자동으로 검출했습니다. 사람이 보정한 것은 스티커에 가린 벽 3~4줄뿐입니다.
- 1·4·5층: 와이파이맵은 열지도가 덮여 있어 자동 검출이 안 됩니다. 그래서 사각형으로 수동 트레이스했습니다.

**부산역 예시** (`source/busan-station/`, 결과는 `data/busan-station/`)

- 평면도는 역사 안의 층별 안내도 사진 1장입니다. **색 채움 모드**(`mode:'fill'`)로 처리합니다. 칠한 칸은 상점·실이 되고, 칠하지 않은 칸은 대합실·통로가 됩니다.
- 레시피는 `node tools/make-busan-recipe.mjs`로 만듭니다.
- 크기 132×75m와 층고 6.5m는 가정값입니다. 근거는 `building.assumed`에 남겨 두었습니다. **건축물대장으로 확인해야 합니다.**
- 트윈에서 보려면 `digital-twin.html?data=data/busan-station/`를 엽니다. 파이프라인 화면에서 보려면 `pipeline.html?sample=busan`을 엽니다.
- 가상 데이터는 `node tools/make-virtual-data.mjs data/busan-station/`로 만듭니다.
- JPEG는 브라우저와 명령줄이 ±1씩 다르게 해독합니다. 해시를 맞추려면 먼저 `node tools/to-png.mjs 파일.jpg`로 PNG로 바꿔 씁니다.

### 평면도 모드

| 모드 | 언제 | 사람이 하는 일 |
|---|---|---|
| `threshold` | 벽이 진한 선인 피난안내도·CAD | 라벨, 가린 벽 |
| `fill` | 실을 색으로 칠한 안내도 | 칠한 색 찍기, 건물 윤곽(footprint), 칠이 안 잡힌 칸은 사각형 |
| `manual` | 열지도 등으로 자동 검출이 안 될 때 | 사각형 트레이스 |

윤곽(`footprint`) 밖은 모두 건물 밖으로 처리합니다. 실 안에 구멍이 있을 수도 있습니다(`holes`). 예를 들어 상점 섬을 둘러싼 대합실이 그렇습니다.

### 에어컨 위치: 있으면 쓰고, 없으면 모델 자리

방마다 아래 순서대로 처음 있는 것을 씁니다. 실내기마다 `source`와 `basis`가 붙습니다. 결과 화면에서는 출처별 색으로 보입니다.

1. **plan**: 도면·설비대장에 표시된 위치, 또는 사람이 고친 위치 (`idu` 작업, `none:true` = 이 방엔 없음)
2. **model**: 위치 예측 모델의 결과 (`minConfidence` 이상만)
3. **photo**: 에어컨 사진에서 센 대수 (모델 결과가 있으면 신뢰도 상위 N개만 쓰고, 모자라면 규칙으로 채움)
4. **estimate**: 면적 40㎡당 1대

모델은 아직 없습니다. 생기면 아래 셋 중 하나로 붙입니다.

- 파이프라인 화면 5단계에서 **모델 입력 내보내기**를 누르거나 `node tools/run-pipeline.mjs 레시피 출력 --model-input 폴더`를 씁니다. 그러면 `model-input.json`(`twin.acplacement.input/v1`)과 층별 `plan-*.png`, `walls-*.png`가 나옵니다.
- 모델이 돌려줄 결과 형식:
  ```json
  { "schema":"twin.acplacement/v1", "model":{"name":"..."},
    "units":[{ "floor":"2F", "x":12.3, "y":4.5, "kind":"4way", "confidence":0.83 },
             { "floor":"2F", "px":[410,220], "confidence":0.7 }] }
  ```
  `px`는 `walls-*.png`의 픽셀 좌표입니다. 미터와의 관계는 `i = (x + margin) × res`, `j = (y + margin) × res`입니다(`res`=20px/m, `margin`=6m, model-input.json의 `raster`에 있음).
- 연결 방법은 셋입니다.
  - 결과 파일을 불러옵니다(레시피 `acModel.file`).
  - `recipe.acModel.endpoint`로 POST합니다.
  - 페이지에 `window.TWIN_AC_MODEL = async input => result`를 넣습니다.

### 사람이 직접 고치기

결과 단계의 **직접 수정**에서 층을 고르고 아래 작업을 합니다.

- **실 속성**: 이름, 용도, 정원을 바꿉니다. `recipe.overrides.rooms`에 들어갑니다.
- **실내기 옮기기·추가·삭제**: 고친 방의 실내기는 `idu` 작업(`from:'사람 수정'`)으로 고정됩니다. 그래서 다시 실행해도 그대로 남습니다.

고친 내용은 모두 레시피에 남습니다. 레시피를 저장하면 명령줄에서도 같은 결과가 나옵니다.

### 호스트 연동 메시지: 평면도 넣기, 실내기 기호 인식

대시보드의 도면 업로드 화면(`src/ingest/PlanIngest.tsx`)은 파이프라인을 `pipeline.html?quick=1&detect=1`로 엽니다. 메시지 코드는 `pipeline/host-bridge.js`(파이프라인)와 `src/ingest/bridge.ts`(대시보드)입니다. 규약 원본은 [도면 변환 규약](../../docs/human/reference/plan-ingest.md)입니다.

| 방향 | 메시지 | 필드 | 처리 |
|---|---|---|---|
| 대시보드 → 파이프라인 | `plans` | `files`(File 목록) | 파일마다 층 행 1개(1F부터)를 만들고 평면도를 채움. PNG, JPG 업로드와 PDF 렌더링 페이지에 사용 |
| 파이프라인 → 대시보드 | `detectRequest` | `id`, `floors`(층 id 목록), `image`(인식용 보정 평면도 PNG Blob), `pxPerM`(인식용 해상도) | `detect=1`일 때 3D 트윈 만들기 중 층 그룹마다 1회 요청 |
| 대시보드 → 파이프라인 | `detectResult` | `id`, `detections`(`{cls, conf, box}`, 보정 이미지 픽셀), `key`(S3 키), `error` | 대시보드가 `POST /plans/detect`로 인식. 서버가 없거나 실패하면 빈 목록과 `error` |
| 파이프라인 → 대시보드 | `buildingRendered`(기존) | `building` | `detect=1`이면 층마다 `background`(`toPlan` = 보정 이미지 픽셀 → m), `detections`, `meta.ingest.warnings`를 붙임 |

- 메시지는 `source`(`maestro` 또는 `twin`)와 부모 창과 iframe 창으로 출처를 확인합니다.
- 인식용 보정 이미지는 화면용 20px/m 보정 이미지와 따로, 원본 이미지에서 다시 보정합니다. 해상도 `pxPerM`은 인식 모델 학습 해상도 80px/m, 원본의 실제 해상도(외곽 4변 중 최대), 여백 포함 긴 변 8000px 중 가장 작은 값입니다(`pipeline/host-bridge.js` `detectRes`).
- 인식용 보정 이미지 픽셀 (u, v)와 평면 좌표의 관계는 `x = u / pxPerM − 6`, `y = v / pxPerM − 6`입니다(`MARGIN` 6m).
- 좌표 변환과 호실 배정은 대시보드(`src/ingest/units.ts`)가 합니다. 인식 결과가 있는 층은 면적 추정 실내기(`source: estimate`)를 빼고, 신뢰도 0.5 미만, `unknown`, 실 밖 실내기는 `review: true`로 표시합니다.
- 대시보드가 응답하지 않으면 6분 뒤 빈 결과로 진행합니다. `detect=1`이 없으면 요청하지 않습니다.

### 실내기 유형별 3D 형상

`building.json`의 `idus[].cls`가 있으면 방 화면이 유형별 형상을 그립니다(`pipeline/idu-shapes.js`). `cls`가 없는 기존 데이터는 이전처럼 `type`, `model` 문자열의 `1WAY` 여부로 1방향 또는 4방향 카세트를 그립니다.

| `cls` | 형상 | 위치 |
|---|---|---|
| `cassette_4way`, `cassette_2way`, `cassette_1way` | 천장 패널과 방향 수만큼의 토출구, 베인 | 천장면 |
| `ceiling_duct` | 천장 위 본체, 천장면 공급구와 흡입구 격자 | 천장면 |
| `wall_mounted` | 얇은 상자, 앞면 아래 토출구 | 바닥에서 2.2m(천장고 − 0.25m 이하) |
| `floor_standing` | 높이 1.8m 상자, 위쪽 앞면 토출구 | 바닥 |
| `unknown` | 4방향 카세트 형상 | 천장면 |

- 토출 방향은 `rot`(도)입니다. 0은 평면 x+(오른쪽), 90은 평면 y+(아래쪽)입니다. 값이 없으면 실 중심 쪽 긴 변 방향입니다.
- 크기는 `size`(`[w, d]`, 평면 x, y 방향 길이, m)이고, 없으면 유형별 기본값을 씁니다.
- 실내기 목록의 모델 칸은 `type`과 `model`을 함께 표시합니다(예: `천장형 4방향 카세트 · ARNU12GTRB4`).

### 스카이뷰로 건물 모양 검증

스카이뷰(지도 항공사진, 북쪽이 위)는 **화면에 깔지 않고** 도면이 실제 건물과 맞는지 확인하는 데만 씁니다. 레시피 `site`에 적습니다.

- `ref`: 도면 점(m)과 사진 점(px)의 짝. 회전·축척·이동을 맞춰 **방위(northDeg)**와 맞춤 오차를 구합니다. 방위는 EnergyPlus의 Building North Axis로 들어가 일사 계산에 쓰입니다.
- `outline`: 사진에서 지붕 바깥 윤곽을 따라 찍은 점(px). `holes`: 중정처럼 뚫린 부분.
- 결과는 `building.json`의 `site.check`에 남습니다.

| 지표 | 뜻 | 경고 기준 |
|---|---|---|
| `iou` | 겹친 넓이 ÷ 합친 넓이 (층 윤곽 합집합 vs 사진 지붕, 0.5m 격자) | 0.8 미만 |
| `areaRatio` | 도면 넓이 ÷ 사진 지붕 넓이 | ±15% 밖 |
| `meanEdgeM`·`maxEdgeM` | 두 경계선 사이 거리 평균·최대 (m) | — |
| `onlyModelM2`·`onlyPhotoM2` | 한쪽에만 있는 넓이 — 어디가 다른지 실마리 | — |

겹쳐 보려면 `node tools/site-overlay.mjs <레시피> <building.json> [출력.png]`를 씁니다. 노란 선은 층 윤곽, 빨간 선은 사진 지붕 윤곽, 하늘색은 실입니다.

- 사진은 비스듬히 찍혀 지붕이 1~2m 밀려 보일 수 있습니다. 평균 경계 차 1m 안팎은 정상입니다.
- 중정은 사진에서 **지붕 안쪽 끝**을 땁니다. 아래층이 중정 쪽으로 더 나와 있으면 도면 넓이가 크게 나옵니다.

#### 모양 보정 (스카이뷰에 맞춰 도면 휘기)

안내도처럼 비율이 어긋난 도면은 파이프라인이 스카이뷰 지붕 윤곽에 맞게 **자동으로 휩니다**.

1. 위에서 본 도면 윤곽(층 윤곽 합집합)의 경계를 일정 간격의 조절점으로 찍습니다.
2. 조절점마다 사진 윤곽의 가장 가까운 점과, 그 조절점을 가장 가깝게 고른 사진 윤곽 점들의 평균을 목표로 잡습니다(양방향 대응).
3. 조절점에서 목표로 가는 박판 스플라인(TPS) 변형을 맞춥니다. 처음에는 거의 아핀(단단하게)으로 시작하고, 반복할수록 조금씩 유연하게 합니다(비강체 ICP).
4. 변형이 도면 안에서 접히거나 지나치게 찌그러지면(야코비안 < 0.15) 직전 단계에서 멈춥니다.

- **적용 범위**: 실, 층 윤곽, 실내기, 중정에 같은 변형을 적용하므로 서로 어긋나지 않습니다. 긴 벽은 2m 간격으로 점을 더해 휜 다음, 거의 일직선인 점은 다시 뺍니다.
- **적용 조건**: 평균 경계 차가 **1.5m 넘을 때**만 씁니다. 그 이하는 사진 오차(비스듬한 촬영, 처마)로 보고 도면을 그대로 둡니다. 또 IoU가 0.01 이상 오를 때만 씁니다.
- **결과 기록**: `site.warp`(변형), `site.checkBefore`(보정 전 지표), `site.check`(보정 후 지표)가 남습니다. 보정하지 않았으면 이유가 `site.fitSkipped`에 남습니다.
- **좌표가 두 가지입니다**
  - 레시피 작업(평면도 표기, 사람 수정, 에어컨 모델 입력·출력)은 **평면도 좌표**를 그대로 씁니다.
  - 결과 화면에서 실내기를 옮기면 `unwarpPoint`로 평면도 좌표로 되돌려 저장합니다.
  - 공조 구역의 실내기를 고치면 원래 공간 전체를 함께 고정합니다.
- **설정**: 레시피 `site.fit`으로 바꿉니다.
  - `{ "enabled":false }`: 보정을 끕니다.
  - `{ "holes":true }`: 중정도 맞춥니다.
  - `minEdgeM`, `minJacobian`, `lambdaMin`, `iters`, `minGain`도 바꿀 수 있습니다.

| 건물 | 보정 전 IoU | 보정 후 IoU | 평균 경계 차 | 크기 |
|---|---|---|---|---|
| 6공학관 | 0.84 | (보정 안 함: 0.5m ≤ 1.5m) | 0.5m | 48×35m |
| 부산역 | 0.62 | 0.88 | 8.7 → 4.0m | 132×75 → 148.9×76.6m |

- 부산역 크기는 스카이뷰 축척(≈0.154 m/px, 안내도 132m 가정에서 나온 값)을 따릅니다. 실측 길이를 하나 알면 축척을 확정할 수 있습니다.
- 트윈의 외피(유리, 멀리언, 테두리)도 층 윤곽을 따라 그립니다.

### 큰 공간을 공조 구역으로 나누기

대합실처럼 실내기가 많은 공간은 **에어컨을 기준으로** 여러 구역으로 나눕니다. 구역마다 EnergyPlus Zone 하나가 되고, 트윈에서도 실 하나로 보입니다. 어느 건물에나 같은 규칙을 씁니다.

1. 실내기가 **8대 넘는** 실만 나눕니다.
2. **실외기(냉매 계통)가 다르면** 한 구역에 섞지 않습니다.
3. 외벽에서 **4.57m 안**은 외주부, 그 안쪽은 내주부로 나눕니다(ASHRAE 90.1 부록 G). 외주부는 향(위·아래·좌·우)별로 나눕니다. 실내기 2대 미만인 묶음은 같은 실외기의 가까운 묶음에 합칩니다.
4. 묶음마다 실내기 **8대 이하**가 되도록 위치로 묶습니다(용량 제한 k-means, 주축 방향 초기값이라 항상 같은 결과).
5. 바닥은 0.5m 격자로 가장 가까운 실내기 묶음에 나눠 줍니다(같은 외주/내주 안에서만). 떨어진 조각은 가장 많이 닿은 구역에 붙입니다.

- 구역 실의 id는 `원래id-1, -2, …`, 이름은 `원래이름 n구역`입니다. `zoneOf`(원래 실)와 `zoneBasis`(실외기 · 외주/내주 · 실내기 대수)가 남고, 트윈 실 정보에 표시됩니다. 정원은 넓이 비율로 나눕니다.
- 기준값은 레시피 `zoning`으로 바꿉니다: `{ "maxIdus":8, "minIdus":2, "perimeter":4.57, "cell":0.5 }`.

### EnergyPlus 시뮬레이션

```
node tools/run-energyplus.mjs data/busan-station/building.json sim/KORAIL-BUSAN [--epw 부산.epw]
```

- **IDF 내용** (EnergyPlus 24.2, 파이프라인 화면에서도 내려받을 수 있음)
  - 실마다 Zone 하나를 만듭니다.
  - 윤곽에 닿는 변은 외벽으로 하고 창을 붙입니다.
  - 내벽과 층간은 단열 경계로 둡니다. 내벽은 실 안 복사와 축열에는 참여합니다.
  - 위층이 덮지 않는 부분에는 지붕을 둡니다.
  - 각 Zone에 IdealLoads를 둡니다. 내부 발열은 용도별 인원, 조명, 기기입니다.
- **실행**
  - EnergyPlus는 `ENERGYPLUS_DIR`, `C:/EnergyPlus*`, 사용자 폴더의 `EnergyPlus*`, PATH 순서로 찾습니다.
  - 찾으면 실행해서 `simulation.json`(`twin.simulation/v1`)을 building.json 옆에 씁니다. 트윈은 이 파일이 있으면 실마다 **피크 냉방부하와 설치 용량 비교**(적정, 용량 부족, 과대 설치)를 보여 줍니다.
  - 찾지 못하면 IDF만 만들고 설치 안내를 출력합니다.
- **기상 조건**: EPW가 없으면 부산 설계일(근사)로 계산합니다. EPW가 있으면 6~9월로 계산합니다.

### 운전 시뮬레이션: 기존 운전 vs 내가 고른 운전

트윈 상단의 **시뮬레이션** 탭에서 조건을 고르고 **EnergyPlus로 계산**을 누릅니다.

- **고를 수 있는 조건**: 설정온도, 운전 시작·끝, 사람이 적은 시간에 끄기, 사전 냉방
- **보여 주는 결과**: 예상 실온, 전력 절감, 요금 절감, 불쾌도
  - 평면도는 실마다 **예상 최고 실온**으로 칠해집니다.
  - 실을 누르면 그 실의 기존 운전과 선택 운전 결과가 나옵니다.

명령줄로 돌리면 결과가 `<데이터 폴더>/scenario.json`에 저장되고, 서버가 없어도 화면이 이 파일을 읽습니다.

```
node tools/run-scenario.mjs data/busan-station/ --sp 26 [--start 07:00 --end 22:00] [--off-empty] [--precool 30] [--epw 부산.epw]
```

| 항목 | 계산 방법 | 근거 |
|---|---|---|
| 예상 실온 | EnergyPlus 열평형 계산. 냉방 용량은 **실에 설치된 실내기 용량 합**까지로 제한합니다. 그래서 용량이 모자라면 설정온도보다 올라갑니다. | EnergyPlus 24.2 (미국 에너지부, ASHRAE 140 검증 엔진) |
| 냉방 전력 | 냉방 열량 ÷ COP. COP는 실내기 정격(냉방능력 ÷ 소비전력)에 외기온도 보정 `1+0.02(T−35)`을 적용합니다. | 설비대장의 실내기 정격 |
| 요금 | 시간별 전력 × 한전 단가. 부산역은 일반용(을) 고압A 선택Ⅱ **계시별** 요금입니다. 기본요금과 부가세는 비교에서 뺐습니다. | [한전 전기요금표](https://cyber.kepco.co.kr/ckepco/front/jsp/CY/E/E/CYEEHP00102.jsp) (2023-11-09 적용분 — 최신 단가 확인 필요) |
| 열 불쾌도 | 재실 시간 동안 쾌적 범위(20~26°C) 밖으로 벗어난 온도 × 시간을 실마다 구해 평균합니다(K·h/실). | BOPTEST KPI `tdis_tot` 정의 |
| 불만족 비율 | Fanger PMV/PPD를 재실 인원으로 가중 평균합니다. 불쾌 비율은 \|PMV\| > 0.5(ISO 7730 B등급 밖)인 비율입니다. 옷 0.5clo(난방철 1.0clo), 기류 0.15m/s를 가정합니다. | ISO 7730 (EnergyPlus 내장) |

- **비교 조건**: 두 운전은 같은 건물, 같은 기상, 같은 내부 발열에서 계산합니다. 결과 차이는 운전 방식의 차이만 반영합니다.
- **BOPTEST를 직접 쓰지 않은 이유**
  - BOPTEST는 자체 테스트 건물만 계산할 수 있습니다.
  - 공개 서버는 인증서 문제로 접속이 안 됐습니다.
  - 그래서 KPI 정의(tdis, 에너지, 비용)만 그대로 가져와 우리 건물의 EnergyPlus 결과에 적용했습니다.
- **기존 운전의 설정온도**: building.json의 `operation.coolSetpoint`를 씁니다. 값이 없으면 24°C로 가정합니다. BMS 설정값으로 바꾸면 정확해집니다.
- **기상 조건**: EPW가 없으면 **여름 설계일 하루**만 계산합니다. 여름 전체(6~9월) 절감액을 보려면 부산 EPW를 `--epw`로 넣습니다.
- **냉방·난방 모드**: 5~9월은 냉방, 그 밖은 난방으로 계산합니다 (웹 데모와 같은 기준). 화면이 `scenario.mode`('cool' / 'heat')를 함께 보냅니다.
  - 난방이면 설정온도를 **난방 설정온도**로 쓰고 냉방은 끕니다. 기존 운전의 난방 설정은 `operation.heatSetpoint`, 없으면 20°C로 가정합니다.
  - 난방 능력은 실내기 `heatKw`, 없으면 냉방 능력 × 1.1로 제한합니다. 전력 = 난방 열량 ÷ COP × 외기 보정 `1+0.02(7−T)`(외기 7°C 정격, 추울수록 효율 저하)입니다.
  - 쾌적 범위는 18~24°C(정부 권장 겨울철 20°C 기준), PMV 계산의 옷은 1.0clo입니다.
  - 실온이 25°C를 넘고 외기보다 2°C 이상 높으면 창을 연다고 봅니다(최대 시간당 3회). 이 가정이 없으면 단열 칸막이 모델에서 꽉 찬 강의실이 30°C를 넘어, 난방이 전혀 필요 없는 것처럼 계산됩니다.
  - 기상 예보(`weather.json`)는 **예보 날짜가 오늘일 때만** 씁니다. 예제 파일은 6월 예보라 겨울에는 쓰지 않고, 남은 시간은 지금 외기를 이어 씁니다.
- **결과 저장**: `sim/<건물>/runs/<해시>/`에 남습니다. 건물, 시나리오, 요금, 기상이 같으면 다시 계산하지 않고 저장된 결과를 씁니다.

```js
// iframe 밖에서
twin.contentWindow.postMessage({ type: 'twin:update', data: snapshot }, '*');
// 같은 페이지에서
DigitalTwin.ingest(snapshot);
```

- **트윈은 실시간 값을 만들지 않습니다.** 받은 값을 그리기만 합니다. (예전의 가상 중앙제어기 `virtual-controller.js`는 지웠습니다.)
- 대시보드(4th-maestro Frontend '에게')에 넣으면 대시보드가 5초마다 보내는 호실 상태(`{source:'maestro', type:'state', data:{time, outdoorTemp, rooms}}`)를 이 형식으로 바꿔 씁니다. 그래서 웹에 보이는 값과 트윈 값이 같습니다.
  - 대시보드의 호실 id·실내기 id는 트윈 `building.json`의 id 그대로입니다. 데모 값도 트윈 도면에서 만듭니다(`node tools/export-web-demo.mjs` → 웹 `public/demo/`, 생성 코드는 `pipeline/web-demo.js`).
  - 건물 목록도 트윈을 따릅니다: `data/buildings.json`(6공학관 `eng6`, 부산역 역사 `busan-station`). 대시보드가 `?building=<id>`로 열면 그 건물 폴더를 읽습니다.
  - 대시보드의 **건물 추가하기**: 도면 이미지를 넣고 파이프라인에서 **트윈에서 렌더링**을 누르면 그때부터 그 건물 데이터가 만들어집니다. 그 전에는 만들지 않습니다.
  - **채팅 what-if**: AI 도우미에 "3층 강의실 18도로 낮추면?"처럼 물으면 대시보드가 `{source:'maestro', type:'simAsk', id, rooms, setpoint, hours}`를 보냅니다.
    - 트윈은 그 방들만 지금부터 N시간(기본 2시간) 설정을 바꿔 계산합니다. 기준은 현재 설정 유지 예측입니다.
    - 두 번 답합니다(노션 3차 초안 설계: what-if는 5R1C, EnergyPlus는 오프라인 보정).
      1. `stage:'fast'`: 브라우저에서 **5R1C**(ISO 13790, `pipeline/rc5.js`)로 수십 ms 안에 계산하고, EnergyPlus 대비 검증 오차(`accuracy`)를 같이 보냅니다.
      2. `stage:'final'`: 계산 서버가 있으면 EnergyPlus로 다시 계산해 바꿉니다(서버에는 `scenario.window = {from, to, sp, rooms}`, 6초 안팎). 즉시 값은 `fast`에 남깁니다. 서버가 없으면 `onlyFast:true`로 5R1C 값만 확정합니다.
    - 결과는 `{source:'twin', type:'simAnswer', id, ok, stage, engine, mode, window, ms, accuracy, fast, onlyFast}`입니다. 대시보드는 답변과 설정온도 스케줄 초안을 대화에 넣고, 최종 답이 오면 같은 메시지를 고칩니다.
    - 시뮬레이션 패널의 결과는 바꾸지 않습니다.

| 난방 | 25.2% | +0.1% | 0.77°C | −7.0% |

이전 계수(가상 날씨 보정)를 같은 실제 기상 검증일로 재면 냉방 NMBE가 +11.3%로 기준(±10%) 밖이었습니다.

- 방마다 EnergyPlus 모델과 같은 형상·재료로 5R1C 계수를 만듭니다(외벽 U≈0.38, 지붕 0.40, 창 1.8·SHGC 0.40, 열용량 165 kJ/m²K). 15분 간격, 3일 예열 후 하루를 계산합니다.
- 난방·냉방을 따로 보정합니다. 날씨가 다른 **보정일 3일**에서 계수 배율(열용량·외피·일사·질량–표면 결합)과 전력 배율을 격자로 고르고, 쓰지 않은 **검증일 2일**에서 오차를 잽니다.
- 목표는 시간별 전력 모양, 실온, **설정 변경 반응**(전 실 2시간 +2°C일 때 전력 변화)을 함께 맞추는 것입니다. what-if 답은 결국 '바꿨을 때의 차이'이기 때문입니다.
- 합격 기준: ASHRAE Guideline 14 시간 단위 CV(RMSE) ≤ 30%, NMBE ±10%.
- 6공학관 결과(검증일):

| 모드 | CV(RMSE) | NMBE | 실온 RMSE | 설정 변경 반응 오차 | 판정 |
|---|---|---|---|---|---|
| 난방 | 25.7% | −0.3% | 0.56°C | −14% | 합격 |
| 냉방 | 7.2% | 3.0% | 0.08°C | −1.2% | 합격 |

- 보정 파일이 없는 건물(부산역, 도면 편집 중인 건물)은 기본 계수로 계산하고 답에 '보정 전 기본 계수'라고 표시합니다.
- 대시보드 없이 혼자 열면 받은 값이 없으므로 도면만 보입니다. `postMessage`·`DigitalTwin.ingest`로 넣으면 그때부터 그립니다.

### 와이파이 접속 수 → 방별 재실 인원

- **AP 위치**: 레시피의 `wifi`에 와이파이 지도(`plans/wifimap-*F.png`)에서 찍은 AP 위치(u, v 비율)를 적습니다. 파이프라인이 이를 도면 좌표로 바꾸고 소속 방을 찾아 `building.json`의 `aps`에 넣습니다.
  - 6공학관은 1~5층에 AP 47대가 있습니다.
  - 지도는 도면을 90° 돌린 방향이라 `orient:'rot90'`입니다.
- **나누는 방법** (`pipeline/occupancy.js`): AP 한 대의 접속 수를 주변 방들이 나눠 가집니다.
  - 몫 = 방 넓이 × 거리 감쇠(σ 6 m, 18 m 밖은 0)이고, AP가 방 안에 있으면 3배입니다. 수업 중인 방은 시간표로 몫을 더 줍니다.
  - 인원 = (접속 수 − 배경 기기) ÷ 1인당 기기 1.3대입니다.
  - 가상 데이터로 왕복 시험한 결과, 전체 인원은 거의 맞았고(442명 → 444명) 방별 평균 오차는 4명 정도였습니다.
- **어느 AP에도 안 잡히는 방**(6공학관 4실)과 **AP가 없는 건물**(부산역)은 `rooms[id].occupancy`(재실 센서)를 쓰고, 그것도 없으면 시간표를 씁니다. 화면 라벨에 출처(와이파이 / 재실 센서 / 시간표)가 표시됩니다.
- **빈 방 냉방 경고**는 실측 재실이 있으면 '재실 0명인데 켜짐'으로 판단합니다.

### 쾌적도 (PMV/PPD)

실시간 쾌적도는 **ISO 7730 PMV/PPD**(Fanger 열수지 모델, `pipeline/comfort.js`)로 계산합니다. EnergyPlus 시뮬레이션의 쾌적도와 같은 모델입니다. 불쾌지수(THI)는 참고값으로만 툴팁에 남겼습니다.

- 계산 절차는 ISO 7730 부록 D와 같고, 부록 D 표의 기준 사례(예: 22°C·60%·0.1m/s·1.2met·0.5clo → PMV −0.75, PPD 17%)와 소수 둘째 자리까지 맞습니다.
- 재지 않는 값은 가정하고, 방 정보에 가정값을 함께 표시합니다.
  - 복사온도: 실온과 같다고 봄
  - 기류: 운전 중 0.15 m/s, 정지 0.1 m/s
  - 옷: 6~9월 0.5clo, 5·10월 0.7, 11~4월 1.0
  - 활동량: 강의·회의·사무 1.1met, 휴게 1.2, 실험·대합실·식당 1.4, 상점 1.6
- 판정 기준:
  - 쾌적: |PMV| < 0.5 (ISO B등급, 불만족 10% 이하). 현장 엔지니어 화면의 '쾌적 비율'에 씁니다.
  - 알림: |PMV| ≥ 0.7 (C등급 밖), 1.5 이상이면 심각
- **쾌적도 지표**(FR-21): 지표 버튼의 **쾌적도**를 고르면 방을 PMV로 칠합니다. 대시보드 버튼(`comfort`)과 연동됩니다.
  - 색은 추움 파랑 · 쾌적 흰색 · 더움 주황이고, 대시보드 범례(`src/heat.ts`의 `COMFORT`)와 같습니다. 실내기가 없는 방은 회색입니다.
  - 평면도 라벨에는 PMV 값을, 층 태그에는 사용 중인 방 중 쾌적(|PMV| < 0.5)한 방 수와 평균 PMV를 표시합니다.
  - 대시보드 자체 3D·호실 상세도 같은 계산(`src/comfort.ts` → `pipeline/comfort.js`)을 씁니다.
- 조치 문구는 계절에 맞춥니다.
  - 난방철에 더움 → 과난방(설정 하향, 절감)
  - 냉방철에 추움 → 과냉방(설정 상향, 절감)
- 한계: 개인의 온열감보다 집단 평균 경향을 보는 지표입니다. 가정값과 센서 위치(천장 흡입구)에 따라 달라지므로, 재실자 설문으로 검증하는 것을 권장합니다.

### 오늘 실측으로 시뮬레이션

화면은 받은 스냅샷을 시간별 평균(재실, 실내기 가동, 설정온도, 전력, 외기)으로 쌓습니다. **운전 시뮬레이션**에서 **오늘 실측 기준**에 체크하면(기본값) 이 기록을 서버로 보내고, 서버는 다음과 같이 하루를 계산합니다.

| 입력 | 지난 시간 | 지금 이후 |
|---|---|---|
| 외기 온도·습도 | 실측 | 기상청 예보 (EnergyPlus 설계일을 시간별 값으로 대체, 하늘 상태로 일사 조정) |
| 방별 재실 | 와이파이·센서 실측 | 시간표(수강 인원), 용도 패턴 × 오늘 실측 비율 |
| 방별 가동 | 실제로 켠 시간 | 운영시간 안에서 사람 있을 때 (빈 방에 켜 두는 습관이면 계속) |
| 설정온도 | 방별 오늘 평균 | 같음 |

- **기존 운전**은 '오늘 실제 운전'입니다. 내가 고른 조건은 방마다 실제로 켠 시간을 유지한 채 운전 시간대, 빈 시간 끄기, 사전 냉방을 적용합니다.
- **실측 보정**: 지난 시간의 실측 실내기 전력 합 ÷ 시뮬레이션 합을 보정 계수로 두고 두 결과에 모두 곱합니다. 계수와 시간별 오차 CV(RMSE)의 보정 전후 값을 함께 보여 줍니다.
- 결과에는 하루 전체 절감과 **지금부터 오늘 끝까지 절감**이 함께 나옵니다.
- 냉방을 끈 시간에는 방에 시간당 2회 환기(문·복도)를 넣습니다. 안쪽 벽을 단열로 보기 때문에, 환기가 없으면 꺼진 방이 40°C 넘게 갇힙니다.

**기간 선택** (대시보드 패널 기준):
- **지금부터 N시간**(기본, 1~8시간): 지금(15분 단위로 내림)부터 N시간 동안만 설정온도를 바꿉니다. 기준은 **현재 설정을 유지했을 때의 예측**(오늘 실제 운전 + 이후 재실 예상)이라, 아직 오지 않은 시간을 실측과 비교하지 않습니다. 시나리오: `{ coolSetpoint, window:{ hours } }`.
- **시간 지정**: 시작·끝 시각, 사람 적은 시간 끄기, 사전 냉방. 기준은 오늘 실제 운전(실측) 또는 기존 운전입니다.
- 결과에는 실제 계산 구간(예: 15:15~17:15)을 항상 표시하고, 구간 전력·요금·실온과 구간이 끝난 뒤 오늘 끝까지의 변화(반등)를 함께 줍니다(`window`).

명령줄에서도 같은 계산을 할 수 있습니다. 결과는 `<데이터 폴더>/live-scenario.json`에 저장됩니다.

```
node tools/run-scenario.mjs data/ --live 실시간.json --sp 26                       # trend가 든 스냅샷 또는 twin.live/v1
node tools/run-scenario.mjs data/ --live 실시간.json --room 3F-6307 --room-sp 26   # 그 방만 바꿔 보기
```

### 방 설정온도 바꿔 보기 → 적용

방 화면의 (i) 패널 아래쪽에서 사용합니다.

1. 슬라이더로 온도를 고르고 **오늘 남은 시간 예측**을 누릅니다. 그 방만 바꾸고 나머지는 오늘 실제 운전 그대로 둔 채 EnergyPlus로 계산합니다.
2. 재실 중 최고·평균 실온, 이 방의 냉방 전력과 요금 변화, 시간별 예상 실온 그래프(지금 설정 vs 바꾼 설정)가 나옵니다.
3. **이 온도로 적용**을 누르면 설정이 바뀝니다.
   - 호스트로 `twin:control {room, setTemp, idus}`(대시보드에는 `{source:'twin', type:'control'}`)를 보냅니다. 명령은 호스트가 실행하고, 바뀐 값이 다음 갱신에 들어옵니다.
   - 대시보드 목업은 기준값에 반영해서 웹·트윈이 함께 바뀝니다.

대시보드에 넣으면 **운전 시뮬레이션** 패널은 트윈 안이 아니라 대시보드 시뮬레이션 탭의 패널에 나옵니다(트윈이 계산하고 결과를 `{source:'twin', type:'sim'}`로 보냄).

대시보드에 넣은 상태(`body.hosted`)에서 트윈은 3D 렌더링과 호실 선택만 합니다(2026-11-20). 상단 바(역할, 데이터 흐름, 설비 연결, 지표, 데이터), 층 칩, 지표 칩, 우측 조치 패널, 범례, 호실 보기 도구를 숨깁니다. 대시보드가 `{source:'maestro', type:'ui', action}`(`persona:<역할>`, `flow`, `pipes`, `back`, `rv:<vol|slice|hum|air>`)으로 숨긴 버튼을 대신 누르고, 트윈은 1초마다 바뀐 경우에만 `{source:'twin', type:'twinUi', ui, kpis, actions}`를 보냅니다. 데이터 파일을 바꾸는 **데이터** 버튼은 관리 기능이라 대시보드에 옮기지 않았습니다.

정적 데이터를 바꾸는 방법은 두 가지입니다.

- 화면 위로 JSON 파일을 끌어다 놓습니다. 상단의 **데이터** 버튼을 누르면 현재 쓰는 데이터 목록이 보입니다.
- 코드로 보냅니다: `postMessage({ type: 'twin:load', kind: 'schedule', data })`.
