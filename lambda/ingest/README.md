## 1. handler 계약: parse, merge, match 3종

**1-1. 모든 요청은 `bucket`(도면 버킷 이름)을 포함하며, parse와 merge 결과 파일은 같은 버킷의 `jobs/<jobId>/`에 저장합니다.**

**표 1.1 parse 요청과 응답**

| 구분 | 필드 | 형식 |
|---|---|---|
| 요청 | `op`, `jobId`, `building`, `bucket` | `"parse"`, 문자열 |
| 요청 | `kind` | `ifc`, `cad`, `pdf`, `image` |
| 요청 | `keys` | 업로드 S3 키 목록 |
| 요청 | `options` | `{scale?: 정수, pxPerM?: 숫자}`, 선택 |
| 응답 | `draftKey` | `jobs/<jobId>/draft.json` |
| 응답 | `detect` | `[{floor, imageKey, pxPerM, toPlan}]`, 인식이 필요한 층 |
| 응답 | `warnings` | 문자열 목록(`meta.ingest.warnings`와 같음) |

- `detect`는 인식 대상이 없어도 항상 목록(빈 목록 포함)입니다.
- 도면 이미지가 있는 층에만 `floors[].background`(`{key, px, toPlan}`)가 있습니다. 이미지가 없는 층에는 `background` 키가 없습니다.

- `detect` 대상은 IFC에서 실내기가 없고 설비도면 이미지가 있는 층, CAD에서 맞는 블록이 없는 층, PDF의 모든 쪽입니다.
- 렌더링한 이미지는 `jobs/<jobId>/pages/<번호>.png`입니다. IFC와 함께 올린 PNG·JPG는 업로드 키를 그대로 `imageKey`로 씁니다.
- `options.scale`은 PDF 축척 분모(예: 200)이며 도면 문자보다 우선합니다. `options.pxPerM`은 IFC와 함께 올린 이미지의 1m당 화소입니다.
- `toPlan`은 CAD 렌더링 이미지만 값이 있고, IFC·PDF 이미지는 `null`입니다.

**표 1.2 merge 요청과 응답**

| 구분 | 필드 | 형식 |
|---|---|---|
| 요청 | `op`, `jobId`, `bucket`, `draftKey` | `"merge"`, 문자열 |
| 요청 | `detections` | `{"<층>": [{cls, conf, box: [u0, v0, u1, v1]}]}` |
| 응답 | `draftKey` | 요청 값 |
| 응답 | `units` | `idus` 수와 `floors[].detections` 중 `cls`가 `door`가 아닌 수의 합 |
| 응답 | `review` | `review: true`인 `idus` 수와 `floors[].detections` 중 `cls`가 `door`가 아닌 수의 합 |

- `background.toPlan`이 있는 층은 상자 중심을 평면 좌표로 바꿔 `idus`(`source: "yolo"`)에 추가합니다. 없는 층은 `floors[].detections`에 저장합니다.
- `cls: door` 결과는 `idus`에 넣지 않습니다. `toPlan`이 있는 층은 1-3절 규칙으로 `floors[].doors`(`source: "yolo"`)에 추가하고, 없는 층은 다른 결과와 함께 `floors[].detections`에 저장합니다.
- 실내기 인식 결과에는 1-4절 규칙으로 용량(`kw`)과 장비 번호(`tag`)를 연결합니다. `toPlan`이 있는 층의 실내기는 `coolKw`, `kwSource`, `tag`, `model`, `modelMatch`를 채웁니다.
- 같은 층을 다시 병합하면 해당 층의 이전 `yolo` 실내기, `yolo` 문, `detections`를 지운 뒤 추가합니다.
- 초안에 없는 층의 결과는 제외하고 `meta.ingest.warnings`에 기록합니다.

**1-2. 초안의 실내기에는 규약 3절 필드 외에 `floor`(층 ID)를 추가합니다.**

호실이 없는 층(PDF)의 실내기는 `room`이 `null`이므로 층을 별도 필드로 기록합니다.

**1-3. 문은 `floors[].doors`에 `{id, a, b, hinge, side, source, conf, review, ref}`로 저장하고, 문이 없는 층에는 키를 두지 않습니다.**

키가 없으면 트윈이 호실마다 임의 문을 생성합니다. 필드 의미의 원본은 [도면 변환 규약](../../docs/human/reference/plan-ingest.md) 3절입니다.

| 필드 | 값 |
|---|---|
| `id` | `D-<층>-<번호>`, 인식 결과는 `D-<층>-Y<인식 번호>` |
| `a`, `b` | 벽 위 문 개구부 양 끝(평면 m, 원점 왼쪽 위, y 아래쪽) |
| `hinge` | 경첩 쪽 끝. 파서는 항상 `a` |
| `side` | 열리는 쪽. `u = (b - a) / 거리`일 때 문짝은 `side·(u.y, -u.x)` 방향(화면 기준 a→b 왼쪽 1, 오른쪽 -1) |
| `source`, `conf` | `ifc` 1, `cad` 문 블록 1·문 호 0.6, `yolo` 인식 신뢰도 |
| `review` | CAD 문 블록의 벽 틈 불일치·폭 범위 밖, 인식 문의 변 불일치·폭 0.6~2.0m 밖·신뢰도 0.5 미만 |
| `ref` | IFC GlobalId, CAD 핸들, 인식 결과 `det-<층 인식 결과 순번>` |

인식 상자는 상자 중심에서 거리가 상자 긴 변 이하인 가장 가까운 호실 변(1e-6m 이내 동률은 앞 변)을 찾습니다. 상자 중심의 투영점을 중심으로 상자 긴 변 길이의 구간을 만들고, 변이 더 길면 구간을 변 안으로 옮깁니다. 맞는 변이 없으면 상자 긴 변 방향 중심선을 쓰고 `review: true`로 둡니다. `side`는 상자 중심이 있는 쪽입니다. 기존 CAD 문과 중점 거리 0.5m 미만인 인식 문은 추가하지 않습니다.

**1-4. 실내기 용량, 장비 번호, 장비일람표는 parse에서 읽고, 모델은 규약 3-5절 순서로 정합니다.**

규칙의 원본은 [도면 변환 규약](../../docs/human/reference/plan-ingest.md) 3-5절입니다. 이 절은 Lambda 구현 범위를 다룹니다.

| 항목 | 구현 |
|---|---|
| 용량 표기 | `(\d{1,3}(?:\.\d)?)\s*kW`(대소문자 무시). 뒤 `이상`·`이하`·`초과`·`미만`, 앞 `~`, 값 0(범례 `00KW`) 제외. `HP`는 읽지 않음 |
| 장비 번호 후보 | 영문 대문자 1~4자와 숫자(`IU-1`, `CAC-01`, `FCU1`, `E-4.5HP`). 숫자만 있는 번호(`01`), 축 번호(`X1`, `Y10`), 한글이 있는 줄의 번호 제외 |
| 연결 | 실내기 또는 인식 상자 중심에서 4.5m 이내 표기를 거리가 가까운 쌍부터 1:1. 용량과 장비 번호는 따로 연결 |
| 장비일람표 | 장비 번호 열(기호, 장비번호, TAG, NO)과 모델 열(모델, 형식, MODEL, 규격) 또는 용량 열(냉방능력, 냉방용량)이 있는 표 |
| 일람표 행 | 장비 번호 열 아래 장비 번호 형식 단어마다 1행. 모델 칸이 모델번호 형식(영문 2자, 숫자 2자 이상, 6자 이상)이 아니면 `name` |
| 모델 순서 | `source`(원본 모델명), `schedule`(일람표 모델), `exact`·`nearest`(`hvac_types.json` `types[].models`), `type`(유형 예시) |
| 용량 대응 | 같은 유형 모델 중 차이 0.05kW 이하는 `exact`(같은 용량은 `market: KR` 우선). 아니면 용량 이상 최소 모델, 없으면 최대 모델로 `nearest`와 `review: true` |

| 저장 위치 | 필드 | 값 |
|---|---|---|
| `idus[]` | `coolKw`, `kwSource` | 용량(kW)과 출처 `pdf-text`, `cad-text`, `ifc`, `schedule`. 일람표 행에 용량이 있으면 `schedule` |
| `idus[]` | `tag`, `model`, `modelMatch` | 장비 번호, 모델, 모델 대응 방식. 용량이 없는 실내기에는 `coolKw` 키가 없음 |
| `floors[].detections[]` | `kw`, `tag` | 위치를 맞추지 않은 층의 인식 결과에 연결한 용량과 장비 번호 |
| `meta.ingest.schedule` | `[{tag, name, model, kw, maker, page}]` | 일람표 행. `page`는 PDF 작업 쪽 번호(`pages/<번호>.png`), CAD 파일 순서 |
| `meta.ingest.texts` | `{"<층>": {pxPerM, kw: [[u, v, kW]], tag: [[u, v, 번호]]}}` | merge 연결용 표기 위치(도면 이미지 화소). 표기가 있는 PDF 쪽과 CAD 렌더링 층만 |

- PDF는 pypdfium2 텍스트 레이어의 글자 상자를 공백으로 나눠 단어를 만들고, `FPDF_PageToDevice`로 페이지 회전을 반영한 렌더링 이미지 화소 좌표로 바꿉니다.
- PDF 단어 처리 규칙은 3개입니다. 줄 끝 `-`(U+FFFE)는 `-`로 바꿉니다. 텍스트 순서로 이어져도 글자 크기 절반 넘게 떨어진 글자는 나눕니다. `-`에서 나뉜 문자 객체(`E-`, `4.5HP`)는 같은 줄 간격이 글자 높이 0.3배 미만이면 잇습니다.
- merge는 `meta.ingest.texts[층].pxPerM`, 없으면 `toPlan` 축척으로 2.5m를 화소로 바꿉니다. 둘 다 없으면 연결하지 않습니다.
- CAD 블록 속성은 `MODEL`·`모델`(모델), `TAG`·`NO`·`기호`·`장비번호`(장비 번호), kW 표기가 있는 값(용량)을 읽습니다. 속성이 없는 항목만 주변 `TEXT`·`MTEXT`와 연결합니다.
- IFC는 `Pset_ManufacturerTypeInformation`의 `ModelReference`, 없으면 `ModelLabel`을 모델로 씁니다. 유형 속성을 상속합니다. 냉방 능력은 이름에 `CoolingCapacity`(현열·잠열 제외) 또는 `냉방능력`·`냉방용량`이 있는 속성이며 100 이상이면 W로 보고 kW로 바꿉니다.

**1-5. match는 본 기호 1개를 정규화 상관으로 같은 도면 이미지에서 찾고, 파일을 저장하지 않습니다.**

규칙의 원본은 [도면 변환 규약](../../docs/human/reference/plan-ingest.md) 3-6절입니다. API `POST /plans/match`(`src/plan_ingest.py`)가 판매사 관리자 권한, `key` 접두어, 값 형식을 검사한 뒤 이 함수를 동기 호출합니다.

**표 1.3 match 요청과 응답**

| 구분 | 필드 | 형식 |
|---|---|---|
| 요청 | `op`, `bucket`, `key` | `"match"`, 도면 버킷, 층 배경 이미지 키(`jobs/<작업>/pages/<번호>.png`, `uploads/<작업>/<파일>.png·jpg`) |
| 요청 | `box` | 본 기호 상자 `[u0, v0, u1, v1]`(도면 이미지 화소). 반올림 후 한 변 8~400px, 이미지 안 |
| 요청 | `min`, `rotate` | 점수 기준(기본 0.35), 0·90·180·270도 회전 포함 여부(기본 true) |
| 응답 | `matches` | `[{box, score}]` 점수 내림차순, 최대 500개. 본 기호 자신 포함. 90·270도 결과는 가로세로를 바꾼 상자 |
| 응답 | `size`, `ms` | 도면 이미지 `[w, h]`, 처리 시간(ms, S3 읽기 포함) |
| 오류 응답 | `status`, `error` | 400(상자 크기·위치, 선 없는 상자, 이미지 형식, 1억 1,000만 화소 초과), 404(이미지 없음). API가 같은 상태 코드로 전달 |

| 단계 | 처리 |
|---|---|
| 흑백 변환 | Pillow `convert('L')` |
| 축소 | 본 기호 짧은 변이 32px가 되도록 도면 전체 축소(`INTER_AREA`). 짧은 변 32px 이하는 원본 크기(확대 안 함) |
| 상관 | OpenCV `matchTemplate` `TM_CCOEFF_NORMED`. 회전마다 계산해 기호 중심 기준 화소별 최댓값과 그 각도 보관 |
| 분할 계산 | 1,024행 띠 단위(띠마다 기호 높이 - 1행 겹침), 띠 2개 동시 계산. 전체 계산과 점수가 소수 셋째 자리까지 같고, 같은 점수가 이어진 선 위에서는 고르는 위치가 다를 수 있음 |
| 중복 제거 | 기호 짧은 변 크기 창의 국소 최댓값 중 `min` 이상을 점수 순으로 채택. 앞 순위 상자와 겹치면 제외 |
| 좌표 | 축소 화소 상자를 축소 비율로 나눠 원본 화소 정수 상자로 환산(오차 1px 이하, 합성 도면 테스트) |

| 1억 화소 쪽 측정(2026-11-21, Apple M4 Pro) | 시간 | 최대 메모리 |
|---|---|---|
| 본 기호 54px(송도 4방향 카세트, 축소 0.59배) | 읽기 0.4초, 찾기 1.2초 | 1.4GB |
| 본 기호 30px, 10px(축소 없음) | 찾기 3.5초 | 2.2~2.3GB |
| 띠 분할 전 전체 계산(회전 2개 동시), 본 기호 30px | 찾기 4.8초 | 5.2GB |

주: `matchTemplate` 호출 1회(3,500만 화소)는 OpenCV 스레드 수 1, 2, 14에서 0.45~0.50초로 같았습니다. 그래서 띠를 2개씩 동시에 계산합니다. 전체 계산은 float64 적분 영상 2장 때문에 함수 메모리(3,008MB)를 넘어 띠 분할로 바꿨습니다. Lambda x86_64 처리 시간은 미측정입니다.

## 2. 형식별 처리: 호실과 실내기 출처

**2-1. IFC는 여러 파일을 층 높이(0.1m 단위)로 묶어 1개 건물로 만듭니다.**

| 항목 | 처리 |
|---|---|
| 층 ID | 모든 층 이름에 층 표기(`1F`, `1층`, `B1F`)가 있고 겹치지 않으면 이름, 아니면 높이 순서(-0.5m 이상 첫 층이 `1F`) |
| 호실 | `IfcSpace` 형상 최저면 다각형. 0.5㎡ 미만과 기존 호실과 80% 이상 겹치는 공간 제외 |
| 실내기 후보 | `IfcEnergyConversionDevice`, `IfcFlowTerminal`, `IfcFlowMovingDevice`, `IfcBuildingElementProxy` |
| 실내기 판정 | 이름·ObjectType·유형 이름이 별칭과 맞으면 신뢰도 1. `IfcUnitaryEquipment`는 별칭이 없으면 치수 판정(신뢰도 0.6) |
| 모델명 | `Pset_ManufacturerTypeInformation`의 `ModelReference`, 없으면 `ModelLabel`(유형 속성 포함). 없으면 1-4절 순서 |
| 냉방 용량 | 이름에 `CoolingCapacity`, `냉방능력`, `냉방용량`이 있는 속성(현열·잠열 능력 제외). 100 이상은 W로 보고 kW로 환산 |
| 문 | `IfcDoor` 배치 x축 방향 구간. 폭은 `OverallWidth`, 없으면 형상 x축 범위. 중심은 형상 x축 범위 중심, 형상이 없으면 배치 원점 |
| 제외 층 | 호실과 실내기가 모두 없는 층(기초 등), 경고로 기록 |

주: 덕트(`IfcFlowSegment`)와 벽 같은 객체는 검사하지 않습니다. 별칭 `duct`, `stand`가 덕트 구간과 `Standard` 이름 객체를 실내기로 판정하기 때문입니다.

**2-2. DXF는 벽 선을 0.5m 팽창해 폭 1.0m 이하 문 개구부를 막은 뒤 벽 사이 빈 영역을 호실로 만듭니다.**

| 항목 | 처리 |
|---|---|
| 단위 | `$INSUNITS`, 없으면 mm |
| 벽 선 | 레이어 이름에 `wall`, `벽`, `구조`가 있는 객체. 없으면 치수·문자·해치·가구·설비 외 레이어의 선 |
| 호실 | 빈 영역을 0.5m 다시 넓혀 벽 면까지 복원. 2㎡ 미만, 건물 바깥, 건물을 둘러싼 도면 틀 안쪽 영역 제외 |
| 실 이름 | 영역 안 `TEXT`·`MTEXT` 앞 2개(면적 문자 제외). `101`, `6107-1` 형식은 `number` |
| 실내기 | 블록 이름 또는 속성 값이 별칭과 맞는 `INSERT`. 위치는 블록 외곽 중심, 속성 태그에 `MODEL`·`모델`이 있으면 모델명 |
| 용량, 장비 번호 | 블록 속성(`TAG`·`NO`·`기호`·`장비번호`, kW 표기 값), 없으면 블록 중심 4.5m 이내 `TEXT`·`MTEXT`(1-4절) |
| 장비일람표 | 도면 안 `TEXT`·`MTEXT` 외곽 상자로 표 머리글과 행을 찾음(1-4절) |
| 문 블록 | 이름이 문 별칭(`DOOR`, `DR`, `문`)과 맞는 `INSERT`. 블록 안 첫 호를 문 호로 처리, 호가 없으면 외곽 상자 긴 변 중심선(`review: true`) |
| 문 호 | 반지름 0.6~2.0m `ARC` 중 중심(경첩)과 한쪽 끝이 벽 선 0.3m 이내이고, 경첩과 그 끝의 중간점이 벽 선에서 0.1m 넘게 떨어진(벽 틈) 호 |
| 층 ID | 파일 이름의 층 표기, 없으면 업로드 순서(`1F`, `2F`), 겹치면 `P<순번>` |
| 렌더링 | 맞는 블록이 없는 층만 1m당 80px 흑백 PNG. `toPlan`을 함께 저장 |

주: 별칭 검사 전에 `_`를 공백으로 바꿉니다. `AC_WM` 같은 블록 이름에서도 `\bwm\b` 별칭이 맞도록 하기 위함입니다.

주: 문 별칭은 앞뒤 영문자를 검사합니다. `DOOR_900`, `DOOR900`, `DR1`, `A-DOOR`, `방화문`은 맞고 `OUTDOOR`(실외기), `DRAIN`, `창문`, `문자`는 제외합니다. 문 블록은 실내기 판정에서 제외합니다. 문 호의 닫힌 쪽 끝은 벽 선 거리로 정하며, 이때 호, 문 레이어, 문 블록은 벽 선에서 뺍니다. 벽 선을 0.5m 팽창해 문 개구부를 막는 호실 생성 규칙은 그대로입니다.

**2-3. DWG는 libredwg `dwg2dxf`로 변환한 뒤 DXF와 같게 처리하고, PDF는 쪽마다 PNG로 렌더링합니다.**

- `dwg2dxf`가 없으면 `RuntimeError('DWG 변환 도구 dwg2dxf(libredwg)가 없습니다. ...')`로 실패합니다.
- PDF 축척 문자는 `1/200`, `1:100`, `S=1/200`, `축척 1/200`, `SCALE 1:50`입니다. 분모는 50~1,200의 표준 축척 12종만 인정하고 `구배 1/100`은 제외합니다.
- 축척을 알면 1m가 80px가 되도록 렌더링하고, 모르면 200dpi로 렌더링해 `pxPerM: null`과 경고를 기록합니다.
- 층 ID는 쪽 문자의 층 표기(`1층`, `일층`, `지하1층`, `1F`) 중 가장 많은 값입니다. 없거나 겹치면 `P<쪽 번호>`입니다.
- PDF 호실은 만들지 않습니다. 트윈 파이프라인 평면도 단계가 쪽 이미지로 호실을 만듭니다.
- PDF 텍스트 레이어에서 쪽마다 용량 표기, 장비 번호 후보, 장비일람표를 읽습니다(1-4절). IFC와 함께 올린 PDF는 읽지 않습니다.

**2-4. PNG·JPG는 EXIF 회전을 적용한 RGB PNG를 `jobs/<작업>/pages/`에 저장합니다.**
파일 이름의 층 표기를 사용하고 없거나 겹치면 `P<번호>`를 사용합니다. 최대 6,400만 화소이며
실제 PNG·JPEG가 아니면 실패합니다. `options.pxPerM`을 인식 입력에 전달하고, 축척이 없으면
경고를 남깁니다. PDF와 마찬가지로 호실은 보정 단계에서 만듭니다.

## 3. 빌드와 배포 설정: 컨테이너 이미지 1개

**3-1. 이미지는 2단계로 빌드합니다. 1단계에서 libredwg 0.13.3을 정적 빌드하고, 2단계에서 `dwg2dxf`와 파이썬 의존성을 설치합니다.**

이미지는 x86_64로 빌드합니다. ifcopenshell 0.9.0.post1 휠은 태그가 `manylinux_2_31`이지만, aarch64 바이너리는 실제로 GLIBC 2.38을 요구합니다. 그래서 Lambda python:3.12 이미지(GLIBC 2.34)에서 import가 실패했습니다(2026-11-20 배포 후 확인). x86_64 바이너리는 GLIBC 2.34를 요구해 실행됩니다. libredwg는 휠이 아닌 C 소스 빌드입니다.

Dockerfile은 의존성 설치 후 네이티브 모듈을 import해 호환성 오류를 빌드 단계에서 검출합니다.
IFC 파서는 소유 SWIG 형상 객체를 유지한 상태로 정점·면 버퍼를 복사해 형상 누락을 방지합니다.

## 5. 제한 사항과 다음 작업

**5-1. 자동 판정이 틀릴 수 있는 경우는 경고 또는 `review: true`로 남기고, 2D 화면에서 운영자가 교정합니다.**

| 항목 | 제한 |
|---|---|
| DXF 호실 | 폭 1.0m 초과 개구부(양개문, 개방 복도)는 닫히지 않아 인접 호실과 합쳐짐. 폭 1.0m 미만 공간은 제외 |
| DXF 벽 | 블록 안 벽, 외부 참조(XREF), 동적 블록 원래 이름(`*U` 이름) 미지원 |
| DXF 실 이름 | 블록 속성으로 쓴 실 이름표 미지원 |
| 여러 CAD 층 | 파일마다 원점이 같다고 가정. 원점이 다르면 층 위치가 어긋남 |
| IFC 치수 판정 | 축 정렬 외곽 상자 기준. 회전한 벽걸이형은 깊이를 크게 계산함 |
| IFC 중복 공간 | 먼저 읽은 파일의 공간 이름을 유지(업로드 순서 의존) |
| PDF 축척 | PDF 용지를 원본 도면 용지로 가정. A1 도면을 A3로 저장한 PDF는 축척이 2배 틀림 |
| PDF 문자 | 문자 층이 없는 스캔 PDF는 축척과 층 표기를 읽지 못함 |
| 건물 크기 | PDF 초안은 호실이 없어 `size`가 0×0 |
| 별칭 | `AC_WALL`처럼 `wall` 단독 표기는 벽걸이형 별칭(`wall mount`, `벽걸이`, `high wall`, `WM`)과 맞지 않음 |
| 문 경첩 | 모든 출처에서 `hinge: a`. IFC는 `OperationType`을 읽지 않아 `side: 1` 고정 |
| IFC 문 위치 | 문 중심선은 배치 원점 기준. 원점이 벽 면에 있으면 벽 중심선에서 벽 두께 절반만큼 떨어짐 |
| IFC 문 중복 | 여러 IFC 파일에 같은 문이 있으면 중복 저장 |
| DXF 문 호 | 벽 레이어가 없는 도면은 문짝 선도 벽 선으로 읽어 닫힌 쪽 끝을 잘못 고를 수 있음. 벽 선이 개구부를 지나는 도면은 문 호를 문으로 보지 않음 |
| 인식 문 | 상자 긴 변을 폭으로 씀. 양개문, 호가 잘린 상자는 폭이 틀릴 수 있음 |
| 용량 표기 거리 | 춘천초 설비도면은 표기와 실내기 중심 거리가 0.96~4.41m. 2.5m 기준으로 37대 중 5대 용량 미연결 |
| 장비 번호 | 숫자만 있는 번호(`01`)와 `-` 없이 나뉜 문자 객체(`CAC` + `01`)는 읽지 않음. `R410A`, `VP25` 같은 규격 문자도 후보가 될 수 있음 |
| 장비일람표 | 두 줄로 나뉜 열 이름(`냉방` / `능력`)과 장비 번호 칸이 빈 행은 읽지 않음. 모델 열이 유형 설명이면 `model` 없이 `name`만 저장 |
| PDF 축척 없음 | `pxPerM`과 `toPlan`이 모두 없으면 인식 결과에 용량·장비 번호를 연결하지 않음 |
| IFC 전력 단위 | 프로젝트 전력 단위를 읽지 않고 값 100 이상을 W로 판정 |
| 기호 찾기 크기·방향 | 본 기호와 같은 축척, 0·90·180·270도만 찾음. 좌우 대칭 사본(거울상), 45도 회전, 크기가 다른 기호는 찾지 못함 |
| 기호 찾기 기준 | 송도 2쪽 실내기 20대 점수 0.35 바로 아래(반올림 0.350)~1.0, 실내기가 아닌 후보 최고 0.341. 기준 0.35에서 문자와 겹친 실내기 1대 누락 |

| 작업 | 기한 | 담당 |
