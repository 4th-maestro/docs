## 1. 역할과 권한: 3개 역할, 서버에서 검사

**1-1. 판매사 총관리자는 기존 Cognito `admin` 그룹이고, 고객사 역할은 구성원 테이블에 저장해 요청마다 서버가 확인합니다.**

| 기능 | 판매사 총관리자 | 고객사 관리자 | 운영자 |
|---|---|---|---|
| 기업 생성·삭제 | 가능 | 불가 | 불가 |
| 기업 코드 발급·재발급·만료 설정 | 가능 | 불가(코드 조회만) | 불가 |
| 건물 생성·삭제 | 가능 | 불가 | 불가 |
| 기업·건물·호실 정보 수정, 도면 교체 | 가능(모든 기업) | 가능(소속 기업) | 불가 |
| 구성원 역할 변경·제외 | 가능 | 가능(소속 기업) | 불가 |
| 관제, AI 질의, 스케줄 저장 | 가능 | 가능 | 가능 |
| 변경 이력 조회, 되돌리기 | 가능 | 가능(소속 기업) | 조회만 |

주: 역할을 토큰 클레임 대신 구성원 테이블에서 읽는 이유는 역할 변경이 다음 요청부터 바로 반영되고, Cognito 토큰 사용자 지정 기능(요금제 의존)이 필요 없기 때문입니다. 요청마다 DynamoDB 조회 1회가 추가되며 Lambda 실행 환경에서 60초 캐시합니다.

## 2. 가입 흐름: 기업 코드, 이메일 인증, 구성원 등록

**2-1. 기업 코드는 가입 전 검사에서 확인하고, 이메일 인증이 끝나면 구성원으로 등록합니다.**

1. 판매사가 관리자 화면에서 기업을 만들면 코드(예: `EGE-7KQ2-M9XD`, 영문 대문자·숫자 8자리, 약 1조 가지)와 만료일(기본 30일)이 생성됩니다.
2. 고객사 사용자는 가입 화면에 이메일, 비밀번호, 기업 코드를 입력합니다.
3. 가입 전 검사(Cognito PreSignUp)가 코드 존재, 만료, 기업 상태를 확인합니다. 실패하면 "기업 코드가 올바르지 않거나 만료되었습니다"로 거부합니다.
4. 이메일 인증 후(Cognito PostConfirmation) 구성원 테이블에 등록합니다. 그 기업의 첫 구성원은 고객사 관리자, 이후는 운영자입니다.
5. 판매사가 코드를 재발급하면 이전 코드로는 가입할 수 없습니다. 이미 가입한 구성원은 유지됩니다.

주: 기존 허용 이메일 목록 가입은 폐지합니다. 기존 사용자는 이전 스크립트로 "데모 기업" 구성원(운영자)으로 등록하고, 판매사 계정(`admin` 그룹)은 유지합니다.

## 3. 데이터 모델: 트윈 테이블 재사용, 기업 테이블 추가

**3-1. 건물·호실은 다른 세션이 배포한 `maestro-twin` 스택의 테이블을 쓰고, 기업·구성원·변경 이력 테이블과 도면 버킷을 추가합니다.**

| 저장소 | 키 | 내용 | 위치 |
|---|---|---|---|
| Companies | `companyId` | 이름, 담당자, 연락처, 상태, 코드, 코드 만료일. 코드 조회용 보조 인덱스 | 신규 |
| Members | `sub` | 기업, 역할(manager·operator), 이메일, 가입일. 기업별 보조 인덱스 | 신규 |
| AuditLog | `companyId` / `시각#id` | 누가, 무엇을(대상·작업), 변경 전 버전, 변경 후 버전 | 신규 |
| Buildings | `buildingId` | 기존 필드 + `companyId`(기업별 보조 인덱스), 현재 도면 버전 | `maestro-twin` 기존 |
| Rooms | `buildingId` / `roomId` | 이름, 층, 용도, 면적. 도면 저장 시 갱신 | `maestro-twin` 기존 |
| 도면 버킷(S3) | `plans/<건물>/v<번호>.json`, `uploads/<건물>/<원본>` | 내장 3D 형식 도면 버전, 업로드 원본 | 신규 |

- `lambda/src/buildings.py`의 `get`, `rooms`, `floors`, `LIST`, `BY_ROOM` 함수 형태는 유지하고 내부 출처만 DynamoDB로 바꿉니다. 이 모듈을 쓰는 11개 모듈(조회, 시뮬레이터, 전력 분석, AI 도구 등)은 수정 범위가 작아집니다. 실행 환경별 60초 캐시를 적용합니다.
- 화면의 3D 도면은 `public/floorplans/<건물>.json` 대신 `GET /buildings/{id}/plan`(현재 버전)으로 받습니다.
- 기존 4개 건물(본관, 업무동, 교육관, 연구동)은 "데모 기업"으로 옮기고, 도면 4개는 버킷 v1로 올립니다.

## 4. 진행 단계: 4단계, 1단계 이후 병렬

**4-1. 1단계는 동작 변화 없이 출처만 바꾸고, 기존 평가 35문항과 화면으로 같은 동작인지 확인한 뒤 2~4단계로 넘어갑니다.**

| 단계 | 내용 | 저장소 | 완료 조건 |
|---|---|---|---|
| 1. 데이터 출처 교체 | `buildings` 모듈 DynamoDB 전환, 도면 버킷·`GET /buildings/{id}/plan`, 데모 기업 이전 스크립트, 3D 도면 API 조회 | Lambda, Frontend | 단위 테스트, 평가 35문항 35/35, 화면 1440px·390px 동일 |
| 2. 기업·회원 | Companies·Members, 코드 가입(PreSignUp·PostConfirmation), API 공통 소속 검사, `/buildings` 기업별 응답, 판매사 기업 관리 화면, 가입 화면 코드 입력 | Lambda, Frontend | 다른 기업 건물 요청 시 403(테스트), 코드 만료·재발급 테스트 |
| 3. 도면 업로드·수정 | 제외(팀원 작업, 2026-11-20 사용자 지시) | 해당 없음 | 해당 없음 |
| 4. 고객사 설정과 마무리 | 고객사 설정 화면(기업 정보, 건물 이름·용도·운영 시간 수정(우리 스택 덮어쓰기 값), 구성원, 이력), 기존 계정 코드 연결(POST /me/join), 사용 중지 기업 구성원 차단, 운영자 수정 버튼 숨김, 문서(설계·요구사항·기술 선택 기록), main 반영·배포 | Lambda, Frontend, docs | 역할별 화면 확인, 문서 검사 |

**4-2. 2단계부터는 Lambda·Frontend를 나눠 에이전트 최대 4개로 병렬 진행할 수 있습니다.**

| 에이전트 | 단계 | 범위 | 브랜치 예 |
|---|---|---|---|
| A | 2 | Lambda 기업·회원·소속 검사 | `feat/tenant-auth` |
| B | 2 | Frontend 판매사 기업 관리, 코드 가입 화면 | `feat/tenant-admin-ui` |
| C | 3 | 취소(도면 수정은 팀원 작업) | 해당 없음 |
| D | 3 | 취소(도면 수정은 팀원 작업) | 해당 없음 |

주: 1단계, 배포, 머지, 공유 자원(AWS 스택, 평가 실행)은 주 작업자가 맡습니다. 에이전트는 별도 worktree에서 브랜치 푸시까지 진행합니다.
