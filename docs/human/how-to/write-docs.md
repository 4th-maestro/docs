# 문서 작성 안내

> **요약** (기준일 2026-11-18)
>
> - 사람용 문서 전체에 보고서 형식 적용. 규칙은 상단 요약, 결론이 담긴 소제목, 비교 기준이 있는 수치, 문서 끝의 다음 작업 4개
> - 말투는 설명 `~입니다.`, 절차 `~하십시오.`. 제목과 표 칸은 명사형
> - 문서 변경의 완료 조건은 `check_docs.py` 명령 2개 통과. PDF 보고서는 devdog `report.py`로 생성
>
> | 항목 | 기준 | 비교 기준 |
> |---|---|---|
> | 요약의 결론 수 | 2~3개 | 넉터 문서 작성 안내와 동일 |
> | 문서 1개 분량 | 2만 자 이하 | 초과 시 `기존이름-주제.md`로 분할 |
> | 표 칸 길이 | 120자 이하 | 초과 시 행 분리 또는 `주:` |
> | 문단 길이 | 300자 이하 | 초과 시 문단 분리 |
>
> **다음 작업**: 없음

새 문서를 작성하기 전에 독자와 목적을 정하십시오. 같은 설명이 이미 있다면 새 파일을 만들지 말고 기존 원본을 수정하십시오. 이 문서의 원본 기준은 넉터 `doc/human/how-to/write-docs.md`입니다.

## 1. 보고서 형식: 규칙 4개와 구성 요소 6개

**1-1. 독자가 문서의 첫 화면과 소제목만 읽고도 결론과 할 일을 알 수 있어야 합니다.**

형식의 기준은 한국은행 「경제전망」(2026년 8월)의 구성입니다. 종결어미는 레퍼런스의 `~이다`를 사용하지 않고 4절의 `~입니다`를 유지합니다.

**표 1.1 규칙 4개: 결론, 소제목, 수치, 다음 작업**

| 규칙 | 피할 예 | 고친 예 |
|---|---|---|
| 첫 화면에 결론 | 배경 설명으로 시작 | 요약에 결론 2~3개와 핵심 수치 표 |
| 소제목에 결론 | `재실 데이터 처리` | `재실 데이터: 5분 단위 구역별 인원으로 집계` |
| 수치에 비교 기준 | `활용률 53%` | `활용률 53%(2024년 38%, 목표 79%)` |
| 끝에 다음 작업 | `개선이 필요합니다` | `2026-11-20까지 히트맵 화면 완성(프론트엔드)` |

**표 1.2 구성 요소 6개: 문서 위에서 아래 순서**

| 요소 | 위치 | 형식 |
|---|---|---|
| 요약 | 제목 바로 아래 | `> **요약** (기준일 YYYY-MM-DD)` 인용 블록 |
| 절 제목 | `##` | `번호. 주제: 결론` 명사구 |
| 주장 문장 | 절의 첫 줄 | `**1-1. 주장 문장.**` 단독 1줄. 근거는 빈 줄 1개 다음 문단 |
| 표와 그림 | 본문 | 위에 `**표 1.1 결론**`, 아래에 `주:`와 `자료:` |
| BOX | 본문 흐름 밖의 상세 설명 | `> **BOX 1** 제목` 인용 블록 |
| 다음 작업 | 문서 끝 | 작업, 기한, 담당 3열 표 |

### 요약 블록

**1-2. 요약은 문서를 열었을 때 스크롤 없이 표시되는 범위에 작성하십시오.**

결론, 핵심 수치, 다음 작업 순서입니다.

```markdown
# 문서 제목

> **요약** (기준일 2026-11-18)
>
> - 결론 1(명사형 종결)
> - 결론 2
>
> | 항목 | 현재 값 | 비교 기준 |
> |---|---|---|
> | 히트맵 갱신 주기 | 5분 | 서울 실시간 도시데이터 인구 갱신 주기 5분 |
>
> **다음 작업**: 2026-11-20까지 히트맵 화면 완성(프론트엔드)
```

- 결론은 2~3개입니다. 독자가 알아야 할 사실과 해야 할 일을 적으십시오.
- 핵심 수치가 없는 문서는 표를 생략합니다.
- 남은 작업이 없으면 `**다음 작업**: 없음`으로 적고 문서 끝의 다음 작업 절을 생략합니다.
- 기준일은 내용을 코드나 운영 상태와 대조한 날짜입니다.

### 절 제목과 주장 문장

**1-3. 절 제목은 `번호. 주제: 결론` 형식의 명사구입니다.**

제목을 순서대로 읽으면 문서의 흐름이 전달되어야 합니다.

- `##` 절에만 번호를 붙입니다. `###` 하위 제목은 번호 없이 주제를 적습니다.
- 주장 문장의 번호는 `절 번호-순번`이며 절 안에서 이어집니다. 예: `1-1.`, `1-2.`
- 주장 문장과 굵은 강조 소제목(예: `**[조사 범위]**`)은 단독 줄에 쓰십시오. 빈 줄 1개를 두고 아래에 내용을 작성합니다(2026-11-18 사용자 결정).
- 절 제목을 바꾸면 기존 앵커를 `<a id="..."></a>`로 남기십시오.
- 다른 문서가 절 번호로 참조하는 문서(디자인 시스템, API 명세)는 기존 절 번호를 유지합니다.

### 표, 그림, 수치

**1-4. 표와 그림 위에는 독자가 읽을 결론을 제목 1줄로 적으십시오.**

절 안에 표가 1개만 있으면 절 제목이 표 제목을 대신합니다.

- 표 번호는 `절 번호.순번`입니다.
- 수치에는 비교 기준을 함께 적으십시오. 비교 기준은 이전 값과 변경일, 상한과 하한, 목표 중 하나입니다.
- 이전 값을 확인할 수 없으면 기준일만 적으십시오. 추정한 값은 적지 않습니다.
- 여러 항목의 비교는 표, 시간에 따른 변화는 그래프(Mermaid)로 작성하십시오.
- 외부 자료의 수치에는 `자료:` 줄로 출처 링크를 적으십시오. 판매 기업 자료와 원문 미확인 수치는 본문이나 `주:`에 표시하십시오.

### BOX와 다음 작업

**1-5. 본문 흐름에서 벗어나는 배경 지식, 사례, 측정 상세는 BOX로 분리하십시오.**

문서의 마지막 절은 남은 작업의 행동, 기한, 담당입니다. 기한이나 담당이 정해지지 않았으면 `미정`으로 적으십시오.

```markdown
## 다음 작업

| 작업 | 기한 | 담당 |
|---|---|---|
| 재실 데이터 생성 스크립트 작성 | 2026-11-19 | 백엔드 |
```

### 분량 상한과 분할

**1-6. 표 칸은 120자, 문단은 300자, 문서 1개는 2만 자 이하입니다.**

초과하면 행 분리, 표 아래 `주:`, 같은 폴더의 `기존이름-주제.md` 분할로 맞추십시오. 분할 예시는 [디지털트윈 조사](../explanation/research/digital-twin-survey.md)와 [논문 상세](../explanation/research/digital-twin-survey-papers.md)입니다.

### 기록 문서

**1-7. 장애 기록과 기술 선택 기록은 요약 추가와 절 제목 정리만 적용합니다.**

과거 기록의 사실 내용은 현재 동작에 맞춰 수정하지 않습니다. 요약의 결론은 원인과 해결(장애 기록), 채택한 방법과 이유(기술 선택 기록)입니다.

### PDF 보고서

**1-8. 발표·제출용 PDF는 devdog `report.py`로 생성하고, Markdown 원본은 `docs/reports/<날짜-주제>/report.md`에 보관하십시오.**

사람용 원본 문서는 `docs/human/`에 두고, PDF는 같은 내용의 특정 시점 출력물로 취급합니다. 문법은 devdog 저장소 `skills/report/references/syntax.md`에 있습니다.

글꼴은 본문 나눔명조, 제목·표·굵은 글씨 Pretendard입니다. 넉터 플랩풋볼 매니저 조사 보고서와 같은 글꼴입니다. `report.md` 앞부분 바로 아래에 기존 보고서의 `<style>` 블록을 복사해 `docs/reports/fonts/`의 TTF 파일을 내장하십시오. 이 블록이 없으면 macOS 시스템 폰트가 Type 3 형식으로 내장되며, PDF 뷰어에 따라 글자 표시가 손상됩니다. `pdffonts report.pdf` 결과에 `Type 3` 행이 없으면 정상입니다.

보고서는 글을 줄이고 도식과 이미지로 전달하십시오. 문제와 수치마다 기사·논문 원문의 핵심 문장을 노란색으로 강조한 캡처를 첨부하고, 그림 아래 `자료:`에 출처를 적으십시오.

| 이미지 | 생성 방법 | 위치 |
|---|---|---|
| 원문 캡처 | `docs/reports/tools/capture.mjs`(강조 문장, 본문 이미지, 첫 화면 3가지) | `docs/human/explanation/research/img/` |
| 논문 PDF 캡처 | `docs/reports/tools/pdfcap.py`(PDF 문장 좌표로 강조 후 주변 영역 저장) | `docs/human/explanation/research/img/` |
| IFC 추출 그림 | `docs/reports/tools/ifc_extract.py`, `ifc_render.py`(호실·설비 추출, 평면·등각 그림) | `docs/human/explanation/research/img/` |
| 데이터 분석 그래프 | 보고서 폴더 `diagrams/build.py`로 HTML 생성 후 `render.mjs`(분석 원본은 `tools/occupancy_analysis.py`) | `docs/human/explanation/research/img/` |
| 도식 | 보고서 폴더 `diagrams/diagrams.html` 작성 후 `render.mjs` 실행 | 같은 폴더 |
| 수치 그래프 | `report.md`의 `::: figure` 차트 JSON | PDF 안에 생성 |

사람용 문서와 PDF는 같은 이미지 파일을 사용합니다. 도식은 PNG로 만들어 넣으십시오. SVG 파일로 넣으면 문서의 내장 폰트가 적용되지 않습니다.

```bash
node docs/reports/tools/capture.mjs '[{"id":"p1-example","url":"https://...","marks":["강조할 문장"]}]' docs/human/explanation/research/img
python3 docs/reports/tools/pdfcap.py targets.json docs/human/explanation/research/img /tmp/pdfcap
node docs/reports/2026-11-18-digital-twin-survey/diagrams/render.mjs
python3 ~/Desktop/Coding/devdog/scripts/report.py docs/reports/2026-11-18-digital-twin-survey/report.md -o docs/reports/2026-11-18-digital-twin-survey/report.pdf
pdffonts docs/reports/2026-11-18-digital-twin-survey/report.pdf
```

두 Node 스크립트는 Playwright를 사용합니다. 기본 경로는 넉터 문서 저장소의 설치본이며, 다른 경로는 `PLAYWRIGHT` 환경변수로 지정하십시오. `pdfcap.py`는 poppler(`pdftotext`, `pdftoppm`)와 Pillow가 필요합니다. 입력 JSON 항목은 `id`, `url`, `marks`이고, 2단 편집 한글 논문은 띄어쓰기를 뺀 문장이 더 잘 검색됩니다. 텍스트 좌표를 추출하지 못하는 PDF는 초록 웹 페이지를 `capture.mjs`로 캡처하십시오.

## 3. 파일 위치: 원본 1곳, 나머지는 링크

**3-1. 같은 설명은 원본 1곳에만 작성하고 다른 문서에서는 링크로 연결하십시오.**

먼저 [원본 문서 위치](../reference/document-locations.md)를 확인하십시오. 사람용 문서와 AI용 문서는 읽는 목적이 다릅니다. AI용 문서는 사람용 원본 문서로 연결하십시오.

## 4. 말투: 설명은 `~입니다`, 절차는 `~하십시오`

**4-1. 설명 문장은 `~입니다.`, 실행을 안내하는 문장은 `~하십시오.`가 기준입니다.**

한 문장에는 한 가지 내용만 적으십시오. 긴 대시로 설명을 덧붙이지 마십시오. 조건·이유·예외는 다음 문장이나 별도 항목으로 나누십시오.

### 제목, 표, 용어

- 제목은 명사형입니다. `~한다`, `~않는다`, `~인가`, `~않게`로 끝나는 문장·질문형 제목은 쓰지 마십시오.
- 표 칸과 목록 항목은 `~함`, `~음`, `~ 여부`나 명사구로 끝냅니다. `~다`로 끝나는 문장은 본문에만 씁니다.
- 대화체와 비유 대신 기술 용어를 쓰십시오. 코드와 서버를 사람처럼 표현하지 마십시오.
- 정보를 더하지 않는 강조·요약 문장은 지우십시오.
- 이 규칙은 문서뿐 아니라 커밋 메시지, PR, 코드 주석에도 적용합니다.

| 피할 표현 | 고친 표현 |
|---|---|
| 다섯 가지 상태를 나눠 준다 (제목) | 응답 상태 |
| 아직 답이 없다 (표 칸) | 아직 응답을 받지 못함 |
| 서버가 넘어졌다 | 서버 오류 |
| 이 5개가 전부입니다 | (삭제) |

devdog 플러그인을 설치했다면 `kolint.py`로 문체 규칙을 검사할 수 있습니다. 확인한 사실, 아직 확인하지 않은 내용, 제안은 구분해 작성하십시오. 비밀값은 문서에 넣지 마십시오.

## 5. 링크와 목록 검사: 명령 2개 통과가 완료 조건

**5-1. 문서를 추가·수정·이동하면 저장소 루트에서 다음 명령 2개를 실행하십시오.**

같은 저장소 안에서는 상대 링크를 사용하십시오. 파일을 이동하면 관련 링크, 폴더 README, [AI 참고 파일 목록](../../ai/sources.json)을 함께 수정하십시오.

```bash
python3 scripts/check_docs.py --write-catalog
python3 scripts/check_docs.py
```

검사 대상은 문서 경로와 링크, 제목 단계, 코드 블록의 언어, 이미지 설명, 파일 목록입니다. 인터넷 주소의 접속 여부와 문서에 적힌 명령의 실제 결과는 별도로 확인하십시오.

## 6. 문서 갱신 기준: 기능 변경과 같은 작업에서 수행

**6-1. 기능을 새로 만들거나 기존 동작을 바꾸는 작업에는 관련 문서 갱신까지 포함입니다.**

AI도 별도 요청을 기다리지 말고 같은 작업에서 문서를 고치십시오.

| 바뀐 내용 | 함께 확인할 문서 |
|---|---|
| API 요청·응답·오류·권한 | API 원본, 연동 안내, 관련 예제 |
| 화면·사용 흐름·로딩·오류 처리 | 화면 설명, [디자인 시스템](../reference/design-system.md) |
| 데이터 구조·시뮬레이션 규칙 | 구조 설명, 데이터 문서 |
| 환경변수·실행 명령·빌드·배포 | 설정 목록, 로컬 실행 안내, 배포 절차 |
| 파일 위치·작업 순서·검사 명령 | 관련 README, `AGENTS.md`, AI 참고 파일 목록 |

### AI 작업 완료 전 확인

1. 바뀐 기능과 관련된 사람용 원본 문서를 갱신하십시오.
2. AI가 참고할 경로·명령·규칙이 바뀌었다면 `AGENTS.md`, AI용 문서, 참고 파일 목록을 갱신하십시오.
3. 파일 추가·이동 시 관련 README와 링크를 고치고 `catalog.json`을 재생성하십시오.
4. 5절의 문서 검사 명령을 실행하고 오류를 고치십시오.
5. 완료 보고에는 갱신한 문서와 검사 결과를 포함하십시오. 실행하지 못한 검사는 실행한 결과와 구분하십시오.
