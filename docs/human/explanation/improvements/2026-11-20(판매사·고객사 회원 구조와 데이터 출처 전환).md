# 판매사·고객사 회원 구조와 데이터 출처 전환

> **요약** (기준일 2026-11-20)
>
> - 허용 이메일 목록 가입을 기업 코드 가입으로 바꾸고, 모든 건물 API에 기업 소속 검사를 넣음. 건물·호실·도면은 고정 파일에서 DynamoDB·S3로 전환
> - 1·2·4단계 운영 배포(Lambda #23, #25, #26, #27, Frontend #17~#20), 배포 서버 13항목 확인
>
> | 항목 | 이전 | 변경 |
> |---|---|---|
> | 가입 | 허용 이메일·도메인 목록 | 기업 코드(가입 전 검사, 인증 후 구성원 등록) |
> | 건물 조회 범위 | 로그인 사용자 전체 | 소속 기업 건물만(다른 기업 403) |
> | 건물·호실 출처 | Lambda 코드 고정 파일 | 트윈 Buildings·Rooms 테이블(60초 캐시) |
> | 도면 출처 | 웹 번들 고정 파일 | S3 도면 버킷(`GET /buildings/{id}/plan`) |
> | 평가 35문항(테이블 출처) | 35/35(파일 출처) | 35/35 |

> **다음 작업**: 없음(고객사 수정 권한은 [판매사 건물 관리와 고객사 관제 전용](2026-11-20%28%ED%8C%90%EB%A7%A4%EC%82%AC%20%EA%B1%B4%EB%AC%BC%20%EA%B4%80%EB%A6%AC%EC%99%80%20%EA%B3%A0%EA%B0%9D%EC%82%AC%20%EA%B4%80%EC%A0%9C%20%EC%A0%84%EC%9A%A9%20%ED%99%94%EB%A9%B4%29.md)으로 변경)

## 1. 배경: 판매사 제공형 서비스

**1-1. 사용자가 판매사가 기업을 만들고 기업 코드로 고객사를 등록하는 구조를 제안했습니다.**

결정 과정과 후보는 [판매사·고객사 회원 구조](../decisions/2026-11-20%28%ED%8C%90%EB%A7%A4%EC%82%AC%C2%B7%EA%B3%A0%EA%B0%9D%EC%82%AC%20%ED%9A%8C%EC%9B%90%20%EA%B5%AC%EC%A1%B0%29.md)입니다.

## 2. 변경: 4단계 중 3단계 반영

**2-1. 데이터 출처 교체, 기업·회원, 고객사 설정 순서로 배포했습니다. 도면 수정 단계는 팀원 작업이라 제외했습니다.**

| 단계 | 내용 | 배포 |
|---|---|---|
| 1 | 건물·호실 DynamoDB, 도면 API·버킷 | Lambda #23, Frontend #17 |
| 2 | 기업 코드 가입, 소속 검사, 판매사 기업 관리 화면 | Lambda #25, Frontend #18 |
| 4 | 기존 계정 코드 연결, 사용 중지 차단, 고객사 설정 | Lambda #26 #27, Frontend #19 #20 |

## 3. 검증: 출처 교체 전후 동일 동작과 배포 서버 확인

**3-1. 호실 533개 내용·순서가 같고, 평가 35문항이 35/35였습니다. 배포 서버는 가입 트리거와 API를 직접 호출해 13항목을 확인했습니다.**
