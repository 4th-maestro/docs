> - 이유: 사용자 제안(2026-11-20). 도면 → 3D 트윈 작업은 판매사가 맡고 고객사는 관제에 집중. 허용 이메일 목록 관리가 필요 없어짐

## 1. 배경: 판매사 제공형 서비스

**1-1. 사용자는 회원을 판매사 총관리자와 고객사(기업 단위)로 나누고, 판매사가 기업 정보와 도면을 등록한 뒤 기업 코드로 고객을 등록하는 흐름을 제안했습니다.**

기존 구조는 허용 이메일·도메인 목록으로 가입을 허용하고, 로그인한 사용자는 모든 건물을 조회했습니다. 건물·호실은 Lambda 코드의 고정 파일, 도면은 웹 번들의 고정 파일이었습니다.

## 2. 평가 대상: 현재 코드의 고정 데이터 사용처

**2-1. 고정 건물 파일을 읽는 Lambda 모듈은 11개이고, 가져올 때 한 번 계산하는 값이 3개 모듈(도구 enum, 전력 분석, 스케줄 검사)에 있었습니다.**

## 3. 측정 방법: 출처 교체 전후 동일 동작 확인

**3-1. 1단계는 실제 테이블과 파일 출처의 데이터를 비교하고, 평가 35문항과 화면으로 같은 동작인지 확인했습니다.**

| 확인 | 결과 |
|---|---|
| 호실 533개 내용·순서 | 동일 |
| 평가 35문항(DynamoDB 출처) | 35/35 |
| 도면 API·대체 경로(가짜 API) | API 응답 시 번들 도면 요청 0회, 실패 시 번들 도면으로 3D 표시 |
| 건물 목록 순서 | 본관, 업무동, 교육관, 연구동 → 본관, 교육관, 연구동, 업무동(테이블에 순서 정보 없음) |

## 4. 후보: 소속 기업 저장 위치 2가지

**4-1. 건물 테이블은 다른 세션의 `maestro-twin` 스택 소유라, 소속 기업은 `maestro` 스택의 별도 테이블에 저장합니다.**

트윈 적재 스크립트(`infra/twin/seed.py`)는 건물 항목 전체를 덮어쓰므로, 같은 항목에 소속 기업 속성을 넣으면 다시 적재할 때 사라집니다.

## 5. 결과: 1단계 동작 동일

**5-1. 1단계 이후 건물·호실은 트윈 테이블, 도면은 도면 버킷에서 읽고, 로컬·테스트는 파일 출처를 유지합니다.**

계획 전체(역할 권한표, 가입 흐름, 데이터 모델, 단계, 위험)는 작업 계획서(`tmp/2026-11-20-tenant-structure-plan.md`, 저장소 미포함)에 있습니다. 확정되는 단계마다 이 기록과 [시스템 설계](../architecture.md)에 반영합니다.

## 6. 결정: 4단계 전환

**6-1. 1단계 데이터 출처 교체, 2단계 기업·회원, 4단계 고객사 설정 화면 순서로 진행합니다. 3단계 도면 업로드·수정은 팀원 작업이라 제외합니다.**

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 건물·호실 DynamoDB, 도면 API·버킷 | 운영 배포(Lambda #23, Frontend #17) |
| 2 | 기업 코드 가입, API 공통 소속 검사, 판매사 기업 관리 화면 | 운영 배포(Lambda #25, Frontend #18) |
| 3 | 도면 업로드·수정 | 제외(팀원 작업, 2026-11-20 사용자 지시) |
| 4 | 기존 계정 코드 연결, 사용 중지 차단, 고객사 설정(기업 정보, 건물 정보, 구성원, 이력), 판매사 구성원·이력 | 운영 배포(Lambda #26, Frontend #19) |

## 7. 운영 시 주의: 배포 순서

**7-1. 배포 순서는 Lambda 배포, 이전 스크립트(`tools/migrate_tenancy.py`), 도면 적재(`tools/upload_plans.py`), 웹 배포입니다(2026-11-20 수행).**

- 적재 전에는 화면이 웹 번들 도면으로 대체하므로 표시는 유지됩니다.
- 건물·호실 테이블이 비어 있으면 모든 건물 API가 실패하므로, 배포 전에 트윈 테이블 적재(2026-11-20 기준 건물 4, 호실 533)를 확인하십시오.
