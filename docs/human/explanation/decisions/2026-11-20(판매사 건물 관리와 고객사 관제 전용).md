## 1. 배경: 고객사 수정 권한 회수

**1-1. 사용자는 판매사가 기업과 기업 내 건물을 관리하고, 기업 코드로 가입한 고객사 계정은 관제 기능만 수행하도록 지시했습니다.**

이전 결정에서는 고객사 관리자가 기업 정보, 건물 이름·용도·운영 시간, 구성원 역할을 수정할 수 있었습니다. 건물 추가는 판매사·고객사 구분 없이 운영 화면의 "건물 추가하기"로 수행했고, 결과는 그 브라우저의 localStorage에만 저장되어 다른 계정과 서버 기능(시뮬레이터, AI 도구, 전력 분석)에서 보이지 않았습니다.

## 2. 평가 대상: 변경 요청 경로와 화면 진입점

**2-1. 서버 변경 경로 4개와 화면 진입점 3곳이 고객사 계정에 열려 있었습니다.**

| 구분 | 대상 |
|---|---|
| 서버 변경 경로 | `PATCH /company`, `PATCH /company/members/{sub}`, `DELETE /company/members/{sub}`, `PATCH /buildings/{id}` |
| 화면 진입점 | 건물 선택 메뉴 "건물 추가하기", 운영 탭 "수정"(평면도 편집), "건물 삭제"(브라우저 목록 숨김) |
| 유지 대상(제어) | `POST /query`, `GET·DELETE /chat`, `POST /schedules`, `DELETE /schedules/{id}`, 조회 API 전체 |

## 3. 측정 방법: 단위 테스트, 교차 검증, 가짜 API 화면

**3-1. 서버는 가짜 테이블·S3 단위 테스트, 화면은 가짜 API로 확인하고, 화면이 만든 등록 요청을 서버 코드에 넣어 교차 검증했습니다.**

- 서버: Lambda 단위 테스트 133개, 트윈 스택 테스트 9개, `sam validate --lint`
- 화면: 1440px 밝은 화면, 390px 어두운 화면에서 고객사·판매사 계정 각각 확인(Playwright)
- 교차 검증: 화면 건물 추가 과정이 만든 POST 본문(제6공학관 샘플, 78,680바이트)을 서버 코드와 가짜 테이블로 처리

## 4. 후보: 트윈 저장 위치 2가지

**4-1. 같은 날 작성된 도면 변환 규약과 이번 작업이 같은 경로(`/buildings/{id}/twin`)를 다른 저장 위치로 정의해, 사용자가 변환 규약 쪽으로 맞추도록 결정했습니다.**

| 항목 | 이번 작업 초안 | 도면 변환 규약 | 채택 |
|---|---|---|---|
| 트윈 파일 | `twin/<id>/building.json` | `plans/<id>/building.json`, `building-v<n>.json` | 변환 규약 |
| 확정 저장 | `PUT /admin/buildings/{id}/twin` | `PUT /buildings/{id}/twin` | 변환 규약 경로 |
| 권한 | 판매사 전용 | 건물 권한(고객사 포함) | 판매사 전용 |
| 요청 본문 | `{twin, rooms, plan}`(화면 변환) | 확정본 `twin`만(서버 변환) | `{twin, rooms, plan}` |

주: 변환 규약 작성 세션이 권한, 본문 형식, 호실 테이블 갱신 방식을 이 결정에 맞춰 규약 4절·6절을 갱신했습니다(2026-11-20).

## 5. 결과: 역할 분리와 판매사 건물 관리 동작

**5-1. 고객사 변경 요청 4개는 403, 제어 요청은 성공하고, 판매사 건물 등록·교체·삭제가 서버에 기록됩니다.**

| 확인 | 결과 |

| 고객사 스케줄 저장·취소 | 201, 200 |
| 화면 등록 본문 → 서버 등록 | 201, 층 5개, 호실 84개, 상태 조회 84실 |

| 같은 건물 id 재등록, 다른 건물과 호실 id 겹침 | 409, 409(겹친 호실 id 최대 5개 표시) |
| 고객사 화면 관리 버튼, 기업 정보 입력란 | 0개, 0개 |

주: 처음 화면 확인에서 고객사 화면이 빈 화면이었고, 가짜 API 데이터의 건물 현황 필드(`now`) 누락이 원인이었습니다. 앱 결함이 아니며 데이터 보완 후 정상입니다.

## 6. 결정: 역할별 기능 분리

**6-1. 고객사는 관제·제어, 판매사는 기업·구성원·건물·도면 관리로 나눕니다.**

| 기능 | 판매사 관리자 | 고객사 관리자 | 운영자 |
|---|---|---|---|
| 기업 생성·수정·삭제, 코드 발급 | 가능 | 불가 | 불가 |
| 구성원 역할 변경·제외 | 가능 | 불가 | 불가 |
| 판매사 관리자 지정·해제(2026-11-21 추가) | 가능(본인 해제 불가) | 불가 | 불가 |
| 건물 추가·정보 수정·도면 교체·도면 편집·삭제 | 가능 | 불가 | 불가 |
| 기업 정보·건물 목록·변경 이력 조회 | 가능 | 가능(기업 코드 제외) | 가능(기업 코드 제외) |
| 관제(현황, 분석, 3D), AI 질의 | 가능 | 가능 | 가능 |
| 제어(스케줄 저장·취소, 추천 적용, 트윈 설정온도) | 가능 | 가능 | 가능 |

**6-2. 건물 추가는 방법 선택, 트윈 파이프라인, 건물 정보 확인, 서버 등록 순서입니다.**

1. 판매사 기업 상세에서 "건물 추가"를 누르고 만들기 방법을 고릅니다. "IFC 파일"은 "준비 중"으로 비활성입니다.
2. 도면 이미지로 트윈 파이프라인을 실행하면 화면이 결과 `building.json`을 받습니다.
3. 화면(`src/admin/convert.ts`)이 건물 id(`b-` + 소문자·숫자 8자)를 만들고, 모든 호실 id에 `<건물 id>.` 접두어를 붙여 호실 목록과 3D 도면으로 변환합니다.
4. 이름·용도·운영 시간·주말 운영을 확인한 뒤 `POST /admin/companies/{id}/buildings`로 등록합니다.
5. 등록 후 새 건물의 운영 대시보드로 이동합니다(2026-11-21 추가, Frontend #77).

주: 호실 id 접두어는 서버가 호실 id를 전체 건물에서 고유하게 가정하기 때문에 필요합니다. 접두어가 없으면 한 건물의 스케줄이 다른 건물의 같은 id 호실에도 적용됩니다.

**6-3. 고객사 관리자 최소 1명 제한은 2026-11-20 사용자 지시로 해제했습니다(Lambda #57).**

판매사는 마지막 고객사 관리자도 운영자로 바꾸거나 소속 해제할 수 있습니다. 고객사 관리자가 0명인 기업의 자동 운영 스위치는 판매사만 변경할 수 있습니다.

**6-4. 판매사 관리자는 기업 관리 화면의 가입한 사용자 목록에서 지정·해제합니다(2026-11-21 사용자 요청, Lambda #66, Frontend #67).**

배경: 고객사 구성원을 고객사 관리자로 바꾼 뒤에도 건물 추가·수정·삭제가 되지 않는다는 문의가 있었습니다. 건물 관리는 판매사 관리자 전용이고, 판매사 관리자 지정은 Cognito 콘솔이나 명령으로만 가능했습니다.

| 결정 항목 | 선택(사용자) | 다른 선택지 |
|---|---|---|
| 반영 시점 | 즉시. 서버가 Cognito `admin` 그룹 구성원을 조회(60초 캐시, 지정·해제 후 API 3초, AI 질의 60초 안) | 토큰 기준 유지(지정은 다시 로그인 후, 해제는 토큰 만료 최대 60분 뒤 반영) |
| 자기 계정 해제 | 금지(버튼 비활성, 서버 409) | 제한 없음(마지막 관리자가 해제하면 AWS 콘솔로만 복구) |
| 지정 대상 | 가입한 모든 사용자. 고객사 소속은 유지하고 판매사 권한 우선, 해제하면 고객사 역할로 복귀 | 소속 없는 사용자만 |

- API: `PUT /admin/users/{sub}/admin`(`{admin}` true 또는 false). 변경 이력은 기업 id `vendor`로 기록하고 화면에는 표시하지 않습니다.
- 화면 메뉴(기업 관리)는 `GET /me` 역할 기준입니다. 대상자는 화면을 새로고침하면 메뉴가 바뀝니다.
- Cognito 그룹 조회가 실패하면 토큰 클레임으로 판정합니다.
- 운영 배포(2026-11-21, Lambda main #67 `3384316`, 웹 main #68 `3922cb9`): 배포 함수 코드 main 일치, `PUT /admin/users/{sub}/admin` 경로(JWT) 확인, 배포 후 10분 API 657건 중 오류·그룹 조회 실패 0건. 운영 계정의 실제 지정·해제는 확인하지 않았습니다.

## 7. 운영 시 주의: 시드 재적재 금지, 삭제 후 잔여 데이터

**7-1. 도면 교체나 건물 삭제 후 `infra/twin/seed.py`를 다시 실행하면 원본 건물 항목과 이전 호실이 다시 생성됩니다.**

- 건물 삭제 후 상태 행 재기록은 시뮬레이터가 매 실행 건물 목록을 다시 읽고 삭제된 건물의 상태 행을 지우도록 수정되었습니다(Lambda #39, 트윈 스택 2026-11-20 20:45 배포). 이전에는 캐시로 1~2분 동안 다시 기록될 수 있었습니다.
- 이력 테이블(Timeseries, Occupancy)은 30일, 대화 기록은 90일 뒤 TTL로 삭제됩니다.
- 트윈 데이터가 없는 건물(2026-11-20 기준 본관, 업무동, 교육관, 연구동)은 운영 탭에서 트윈 화면 대신 내장 3D 도면을 표시합니다.
- 새 건물 3D 도면에는 실내기가 연결된 호실만 포함되어 복도·화장실·계단실은 내장 3D에 표시되지 않습니다.
- 배포 서버의 등록·교체·삭제 동작, 실제 평면도 이미지로 진행하는 파이프라인 전 과정은 확인하지 않았습니다.
- 배포 후 확인(2026-11-20, Lambda 직접 호출): 판매사 기업 상세 200(건물 4곳 `hasTwin` false, 운영 시간 포함), 판매사 건물 목록 200. 고객사 구성원 경로는 운영 구성원 테이블에 검증용 행을 넣는 작업이 거부되어 확인하지 못했고, 단위 테스트로만 확인했습니다.
