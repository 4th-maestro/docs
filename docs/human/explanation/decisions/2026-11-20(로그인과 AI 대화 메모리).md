# 로그인과 AI 대화 메모리

> **요약** (기준일 2026-11-20)
>
> - 채택: 로그인은 Amazon Cognito(관리자 발급 계정, 이메일·비밀번호, 첫 로그인 비밀번호 변경), 전체 화면·HTTP API·WebSocket에 적용
> - 채택: AI 대화는 원문 대화를 Bedrock에 보내지 않고 1KB 이하 대화 메모리만 프롬프트에 넣음. 메모리는 DynamoDB 24시간 TTL, 대화 기록은 90일 보관
> - 이유: 사용자 결정 3건(2026-11-20). 로그인으로 공개 API의 Bedrock 비용 위험 해소, 메모리 요약으로 질의당 입력 토큰을 원문 대화 대비 일정하게 유지
>
> | 항목 | 채택 | 탈락 |
> |---|---|---|
> | 메모리 저장소 | DynamoDB + TTL | ElastiCache Serverless, Lambda 메모리 |
> | 로그인 | Cognito 관리자 발급 | Cognito + 구글, 자체 가입 |
> | 적용 범위 | 전체 화면과 API | AI 채팅·저장만 |
>
> **다음 작업**: 운영자 계정 발급, 로그인 후 화면 실서버 확인(미정)

주: 가입 방식(관리자 발급, 자체 가입 없음)은 [허용 목록 회원가입](2026-11-20%28%ED%97%88%EC%9A%A9%20%EB%AA%A9%EB%A1%9D%20%ED%9A%8C%EC%9B%90%EA%B0%80%EC%9E%85%29.md)으로 대체되었습니다(2026-11-20). 대화 메모리 결정은 유지합니다.

[시스템 설계](../architecture.md) 2절의 인증과 7절 자연어 질의에 적용한 결정입니다.

## 1. 배경: 채팅형 AI와 로그인 요청

**1-1. 운영자가 AI 응답을 메신저처럼 이어서 보고, 기록을 서버에 남기려면 사용자 구분이 필요했습니다.**

2026-11-20 사용자 요청은 3가지입니다. AI 응답을 채팅형으로 표시하고, 이전 대화를 이어서 해석하고, 대화 기록을 서버에 저장하되 로그인을 두는 것입니다. 사용자는 "history 자체를 Bedrock 채팅에 두지 말고 따로 메모리캐시화"하는 방식을 지정했습니다.

## 2. 평가 대상: 후속 질문 해석과 비용

**2-1. 후속 질문("그중 2층만", "방금 것 취소")을 해석할 정보만 남기는 것이 목표였습니다.**

| 항목 | 기준 |
|---|---|
| 후속 질문 해석 | 마지막 질문, 조건 칩, 대상 호실, 초안, 저장한 스케줄 |
| 프롬프트 크기 | 대화 길이와 무관하게 일정 |
| 고정비 | 해커톤 기간 0원에 가깝게 |

## 3. 측정 방법: 구성 비교

**3-1. 실측 없이 구성 요건과 기존 스택 적합성으로 비교했습니다.**

호출 지연과 비용은 측정하지 않았습니다. 메모리 크기 상한(1KB)은 단위 테스트로 확인합니다(`lambda/tests/test_chat.py`).

## 4. 후보: 저장소 3종, 로그인 3종, 범위 2종

**4-1. 저장소는 이미 쓰는 DynamoDB가 VPC 없이 바로 쓸 수 있어 유리했습니다.**

| 후보 | 장점 | 제약 |
|---|---|---|
| DynamoDB + TTL | 서버리스, 기존 스케줄 테이블과 같은 방식, VPC 불필요 | TTL 삭제는 최대 수십 분 지연(코드에서 만료 시각 직접 확인) |
| ElastiCache Serverless(Valkey) | 1ms대 인메모리 조회 | Lambda VPC 배치와 Bedrock·DynamoDB·WebSocket용 VPC 엔드포인트 필요, 월 고정비 |
| Lambda 메모리 | 추가 자원 없음 | 콜드 스타트·다른 실행 환경에서 소실 |

| 로그인 후보 | 판단 |
|---|---|
| Cognito, 관리자 발급 | 채택. 운영자 계정만 사용, 비용 남용 차단 |
| Cognito + 구글 | 탈락. Google Cloud OAuth 클라이언트 생성 필요 |
| Cognito, 자체 가입 | 탈락. 누구나 가입해 Bedrock 비용 발생 가능 |

## 5. 결과: 구성

**5-1. 인증은 HTTP API JWT 권한 부여자와 WebSocket REQUEST 권한 부여자 2개로 구성했습니다.**

| 구성 | 내용 |
|---|---|
| 사용자 풀 | 이메일 로그인, 자체 가입 없음, 비밀번호 10자 이상·소문자·숫자, 복구는 관리자만 |
| 앱 클라이언트 | 비밀 키 없음, USER_PASSWORD_AUTH와 갱신 토큰, 액세스 토큰 60분, 갱신 토큰 30일 |
| HTTP API | 기본 JWT 권한 부여자(액세스 토큰), CORS 사전 요청 제외 |
| WebSocket | 연결 시 쿼리 token 검증(`lambda/src/auth.py`), 토큰의 iss·client_id 확인 후 GetUser 호출 |
| 대화 테이블 | pk·sk, 기록 90일·메모리 24시간 TTL(`lambda/src/chat.py`) |

배포 후 확인: 토큰 없는 호출과 잘못된 토큰은 HTTP 401, WebSocket 연결 거부. 틀린 비밀번호는 로그인 화면에 오류 문구 표시.

## 6. 결정: Cognito 관리자 발급, DynamoDB 메모리

**6-1. 계정이 없으면 화면과 API를 모두 쓸 수 없고, AI에는 대화 메모리 요약만 전달합니다.**

GetUser는 다른 사용자 풀이 발급한 토큰도 통과시키므로 WebSocket 인증은 토큰의 iss와 client_id를 먼저 확인합니다. 브라우저 WebSocket은 헤더를 지정할 수 없어 토큰을 쿼리로 전달합니다.

## 7. 운영 시 주의: 계정 발급과 토큰 보관

**7-1. 계정은 관리자가 AWS CLI로 발급하고, 토큰은 브라우저 localStorage에 보관합니다.**

- 계정 발급 명령은 [lambda README](../../../../lambda/README.md)에 있습니다. 임시 비밀번호는 첫 로그인 때 바뀝니다.
- localStorage 토큰은 XSS 발생 시 노출될 수 있습니다. 사용자 입력 HTML을 표시하는 기능이 생기면 보관 방식을 바꾸십시오.
- WebSocket 쿼리 토큰은 API Gateway 접근 로그를 켜면 기록될 수 있습니다. 접근 로그를 켤 때 쿼리 문자열을 제외하십시오.
