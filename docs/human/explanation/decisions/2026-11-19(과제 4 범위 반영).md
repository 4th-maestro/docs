# 과제 4 범위 반영

> **요약** (기준일 2026-11-19)
>
> - 채택: 해커톤 과제 4(ES 클라우드)의 범위를 서비스 중심으로 변경. 사용자는 건물 운영자, 설비는 실내기(IDU), 핵심 기능은 도면 파싱부터 최적 제어 추천까지 6단계
> - 이전 기획(정비 기술자용 기계실 공조 고장 진단)은 "경계 확장" 모듈로 유지. 기존 서비스 기획·시스템 설계·요구사항 문서는 과제 기준으로 갱신
> - 데이터는 부산대 건물 1개(요청 중)가 1순위이고, 대안은 buildingSMART 커뮤니티 공개 IFC(의원 건물)로 추출 실험 완료
>
> **다음 작업**: 부산대 건물 도면 제공 여부 확인(팀 전체, 미정)

이 기록은 [해커톤 주제 확정](2026-11-19%28%ED%95%B4%EC%BB%A4%ED%86%A4%20%EC%A3%BC%EC%A0%9C%20%ED%99%95%EC%A0%95%29.md)을 대체합니다. 서비스 내용은 [서비스 기획](../service-plan.md)에 있습니다.

## 1. 배경: 과제 공고 내용 확인

**1-1. 2026-11-19에 과제 4의 문제, 목표, 주요 기능, 제공 데이터, 구현 흐름을 확인했습니다.**

| 항목 | 과제 4 내용 |
|---|---|
| 출제 | ES 클라우드(냉난방·환기 B2B, BECON BMS·Cloud) |
| 문제 | 건물 운영자는 공간 현황과 설비 상태를 직관적으로 파악하기 어려움 |
| 목표 | 도면 자동 분석, 3D 디지털트윈 생성, AI 기반 운영 서비스 |
| 주요 기능 | 2D→3D, 공간-설비 자동 매핑, 실시간 상태 시각화, 사용량 기반 최적 제어 추천, 자연어 질의 |
| 데이터 | 부산대 건물 1개(평면도 PDF, IFC·CAD, 층·호실, 설비 배치도), 대안 buildingSMART 샘플, 설비 데이터는 가상 생성 |
| 조건 | 경계를 넘어도 됨, 실제 설비 제어 없이 시뮬레이션 |
| 평가 관점 | 고객이 누구인지, 문제 해결 생각, 눈으로 이해되게 보여 주기 |

## 2. 평가 대상: 방향 3개

**2-1. 과제 중심 + 고장 탐지 확장, 과제 범위만, 기존 기획 유지 + 과제 기능 추가 3개를 검토했습니다.**

| 후보 | 장점 | 단점 |
|---|---|---|
| 과제 중심 + 고장 탐지 확장 | 과제 요구 6단계 충족, 이전 설계 재사용 | 확장 모듈 일정 압박 |
| 과제 범위만 | 범위 명확 | "경계를 넘어도 됨" 조건 미활용 |
| 기존 기획 유지 + 과제 기능 추가 | 이전 문서 재사용 | 과제가 정한 고객(건물 운영자)과 불일치 |

## 3. 측정 방법: 별도 측정 없음

**3-1. 방향은 사용자 질문 답변으로 정했으며, 데이터 대안만 실험으로 확인했습니다.**

공개 IFC 추출 실험은 [공개 IFC 샘플 검토와 추출 실험](../research/ifc-sample-feasibility.md)에 있습니다.

## 4. 결과: 데이터 대안 확인

**4-1. buildingSMART 인증 샘플은 1개 층·공간 2개로 작고, 커뮤니티 의원 건물 IFC는 호실 269개를 추출했습니다.**

## 5. 결정: 과제 중심 + 고장 탐지 확장

**5-1. 사용자 답변(2026-11-19)으로 과제 중심 방향과 기존 문서 갱신을 정했습니다.**

| 항목 | 이전 | 변경 |
|---|---|---|
| 사용자 | 정비 기술자 | 건물 운영자(정비 기술자는 확장 사용자) |
| 대상 설비 | 기계실 공조기·냉동기·펌프 | 호실 실내기(IDU) |
| 핵심 기능 | 고장 원인 진단 | 상태 시각화, 자연어 질의·스케줄, 최적 제어 추천 |
| 데이터 | LBNL 고장 데이터, BOPTEST | 부산대 건물 또는 공개 IFC, 가상 IDU 데이터 |
| 고장 진단 | 핵심 | 경계 확장 모듈(설정온도 미도달 실내기) |

## 6. 운영 시 주의: 실제 제어 금지, 가상 데이터 표시

**6-1. 모든 제어 명령은 스케줄 저장과 시뮬레이션까지만 수행하고, 화면에 가상 데이터임을 표시합니다.**
