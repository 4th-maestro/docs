# PDF 등록 건물 목록 누락

> **요약** (기준일 2026-11-21)
>
> - 판매사 화면에서 PDF 도면으로 등록한 건물(`b-b0qrpf21`)이 상단 건물 선택 목록에 표시되지 않는다는 보고가 있었음
> - 원인은 API 실행 환경별 건물 캐시(60초). 등록을 처리한 실행 환경만 캐시를 비웠고, 화면은 등록 후 목록을 1회만 다시 조회해 이전 목록을 가진 다른 실행 환경의 응답을 받을 수 있었음. 다음 조회는 60초 뒤
> - 서버는 변경 표시(`plans/_rev`)로 다른 실행 환경이 3초 안에 다시 읽도록 수정(Lambda #59). 화면은 등록 후 즉시와 4초 뒤 2회 조회하고, 목록 오류를 목업으로 바꾸지 않도록 수정(Frontend #49)
>
> | 항목 | 수정 전 | 수정 후 |
> |---|---|---|
> | 다른 실행 환경의 새 건물 반영 | 최대 60초 | 최대 3초 |
> | 건물 변경 후 목록 요청 | 1건(즉시) | 2건(즉시, 4초 뒤) |
> | 가짜 API 변경 5.5초 뒤 새 건물 표시 | 미표시 | 표시 |
> | 목록 요청 실패 시 화면 | 목업 목록(서버 건물 없음) | 오류 문구 |
>
> **다음 작업**: main 반영, 배포 후 운영 사이트에서 PDF 등록 직후 목록 확인

## 1. 증상: 등록한 건물이 목록에 없음

**1-1. 2026-11-21 사용자가 PDF로 추가한 건물이 건물 선택 목록에 표시되지 않는다고 보고했습니다.**

배경: 판매사 화면의 건물 추가는 PDF 도면 변환을 임시 id(`b-6wgb8by3`)로 실행하고, 저장할 때 새 id로 건물을 만듭니다. 건물은 2026-11-20 15:02:52(UTC)에 `b-b0qrpf21`(호실 75개, 도면 파일 4개)로 저장됐습니다. 상단 건물 선택 목록은 `GET /buildings` 응답이고, 화면은 60초마다 다시 조회합니다.

## 2. 조사 과정: 저장 데이터, 서버 응답, 실행 환경 수

**2-1. 저장 데이터와 조사 시점 서버 응답은 정상이었고, 등록 시각에 API 실행 환경 5개가 요청을 나눠 처리했습니다.**

| 확인 | 결과 |
|---|---|
| 건물 테이블(읽기 전용 조회) | `b-b0qrpf21` 저장, 소속 기업 있음, 호실 75개 |
| 조사 시점 `GET /buildings` 직접 호출 2회 | 2회 모두 `b-b0qrpf21` 포함 |
| API 로그 3시간 오류(Traceback, ERROR, 시간 초과) | 0건 |
| 등록 전후 15:01:30~15:06:00(UTC) API 실행 환경 | 5개 |
| 화면 코드 | 건물 변경 이벤트 후 목록 1회 조회, 이후 60초 주기 |
| 목록 요청 실패 처리 | 목업 목록으로 대체 |

| 가설 | 판단 | 근거 |
|---|---|---|
| 건물 저장 누락 | 제외 | 테이블과 직접 호출에 건물 있음 |
| 서버 오류 | 제외 | 로그 오류 0건 |
| 다른 실행 환경의 이전 캐시 | 원인 | 쓰기 요청은 처리한 실행 환경의 캐시만 비움, 실행 환경 5개 |
| 목록 오류의 목업 대체 | 가능 경로 | 코드로 확인, 이번 발생 여부는 미확인. 실패 1회로 다음 성공 조회까지 서버 건물이 모두 빠짐 |

## 3. 원인: 실행 환경별 캐시와 1회 재조회

**3-1. 등록 요청을 처리한 실행 환경만 건물 캐시를 비웠고, 화면의 재조회 1건은 이전 목록을 가진 다른 실행 환경이 처리할 수 있었습니다.**

- 서버는 건물 목록을 실행 환경별로 60초 캐시합니다(`buildings.TTL`). 쓰기 요청은 같은 실행 환경의 캐시만 비웠습니다(`buildings.forget`, `tenant.forget`).
- 캐시에 없는 건물 id 요청은 목록을 다시 읽습니다(Lambda #55, [전력 분석 인증 누락과 목업 대체](2026-11-20%28%EC%A0%84%EB%A0%A5%20%EB%B6%84%EC%84%9D%20%EC%9D%B8%EC%A6%9D%20%EB%88%84%EB%9D%BD%EA%B3%BC%20%EB%AA%A9%EC%97%85%20%EB%8C%80%EC%B2%B4%29.md)). 목록 요청은 건물 id가 없어 이 보완이 적용되지 않았습니다.
- 화면은 등록 후 목록을 1회 조회했습니다. 이 요청이 이전 목록을 받으면 다음 주기 조회(60초)까지 새 건물이 표시되지 않았습니다.

## 4. 해결: 변경 표시와 2회 재조회

**4-1. 서버는 쓰기 요청마다 변경 표시를 갱신하고, 화면은 등록 후 4초 뒤 한 번 더 조회합니다.**

| 위치 | 수정 |
|---|---|
| 서버 쓰기 | 건물 등록·수정·삭제, 소속, 구성원, 기업 상태 변경 시 도면 버킷 `plans/_rev` 갱신(`tenant.changed`) |
| 서버 조회 | 각 실행 환경이 3초마다 `plans/_rev` ETag 비교, 다르면 건물·소속 캐시 삭제(`buildings._data`) |
| 서버 실패 처리 | 변경 표시 조회·갱신 실패 시 기존 60초 캐시로 동작 |
| 화면 재조회 | 건물 변경 이벤트 후 즉시와 4초 뒤 목록 조회 |
| 화면 `usePoll` | `reload`를 고정 함수로 변경. 렌더링마다 이벤트 처리기를 다시 등록하면 4초 뒤 조회가 취소됨 |
| 화면 목록 오류 | API 주소가 있으면 목업으로 대체하지 않고 오류 표시 |

변경 표시 확인은 실행 환경당 3초에 최대 1회 S3 HEAD 요청입니다. 실행 환경 5개가 상시 요청을 받으면 월 약 432만 건이고, 서울 리전 GET 계열 단가(1,000건당 0.00035달러, 추정)로 월 약 1.5달러입니다.

## 5. 검증: 단위 테스트와 가짜 API

**5-1. Lambda 단위 테스트 169개가 통과했고, 가짜 API에서 변경 5.5초 뒤 새 건물 표시를 확인했습니다.**

| 확인 | 결과 |
|---|---|
| `RevMarkerTest`(추가) | 다른 실행 환경 쓰기 후 다시 읽음, 확인 간격 전에는 캐시 사용 |
| `test_delete_building`(수정) | 남은 키에 변경 표시 추가 |
| 가짜 API(변경 직후 첫 응답만 이전 목록) | 수정 전 요청 1건, 5.5초 뒤 미표시. 수정 후 요청 2건(4ms, 4,011ms), 표시 |
| 가짜 API 목록 500 응답 | 목업 목록 대신 오류 문구 |
| 운영 탭 자동 운영 카드, 상단 지표 카드(1440px) | 변화 없음 |

주: 수정 전 측정 빌드는 4초 뒤 조회가 처리기 재등록으로 취소된 중간 빌드입니다. 이벤트 후 요청 수(1건)는 수정 전 코드와 같습니다.

## 6. 교훈: 실행 환경별 캐시의 쓰기 반영 경로

**6-1. 실행 환경별 캐시를 쓰는 서버는 다른 실행 환경에 쓰기를 알리는 경로가 필요합니다.**

같은 실행 환경의 캐시 비우기는 동시 실행 환경이 1개일 때만 유효합니다. 화면의 재조회 1회도 같은 이유로 이전 값을 받을 수 있습니다.

## 7. 같은 증상 재발 시 확인 순서

1. `GET /buildings`를 여러 번 직접 호출해 새 건물 포함 여부가 요청마다 다른지 확인하십시오.
2. 도면 버킷의 `plans/_rev` 수정 시각이 등록 시각과 같은지 확인하십시오(`aws s3api head-object`).
3. 브라우저 개발자 도구에서 등록 후 `GET /buildings` 요청이 2건(즉시, 4초 뒤)인지 확인하십시오.
4. 목록 대신 오류 문구가 보이면 해당 요청의 응답 코드를 확인하십시오.
