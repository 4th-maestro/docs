# 트윈 로딩 중 이전 화면 노출과 지연

> **요약** (기준일 2026-11-20)
>
> - 운영 사이트의 3D 디지털트윈이 로딩 중 트윈 자체 도구 줄·지표 칩·층 버튼(앱 임베드 전 화면)을 잠깐 표시함. 시뮬레이션 카드의 입력은 "시간 지정"에서 "지금부터·운전 시간"으로 바뀜. 로딩도 느림
> - 원인은 트윈이 앱 데이터를 받기 전에 자체 화면과 자체 계산값을 먼저 표시·보고하는 순서. 지연 원인은 이 순서에 더해 CloudFront 압축 꺼짐, 트윈 도면이 없는 건물에서도 트윈 화면을 불러온 뒤 내장 3D로 바꾸는 흐름
> - 트윈은 첫 표시부터 임베드 모드, 앱 데이터 수신 후 보고. 앱은 자리 표시 고정, 트윈 도면 미리 조회, 트윈 없는 건물은 트윈 화면을 불러오지 않음. CloudFront 압축과 캐시 헤더 적용
>
> | 항목(네트워크 지연 80ms, 10Mbps, API 300ms) | 수정 전 | 수정 후 |
> |---|---|---|
> | 트윈 자체 화면 노출(0.1초 간격 측정 8초) | 14회 | 0회 |
> | 시뮬레이션 입력 형식 바뀜 | 1회 | 0회 |

## 1. 증상: 이전 화면 노출, 입력 바뀜, 지연

**1-1. 2026-11-20 사용자가 운영 사이트에서 세 가지 증상을 보고했습니다.**

| 증상 | 사용자 표현 |
|---|---|
| 3D 트윈이 이전 버전으로 잠깐 보였다가 정상으로 돌아옴 | "이전 버전으로 살짝동안 보이다가 다시 정상적으로 돌아오는 점" |
| 시뮬레이션 카드의 드롭다운 내용이 갑자기 바뀜 | "토글다운에 있는 내용이 갑자기 바뀌는 듯한 느낌" |
| 로딩 시간 지연 | "로딩시간 지연문제" |

배경: 운영 탭의 3D 영역은 트윈 화면(`twin/digital-twin.html`)을 iframe으로 넣습니다. 앱 안에서는 트윈 자체 도구 줄·지표·패널을 숨기고(`body.hosted`) 앱 카드가 대신 표시합니다(Frontend #29). 트윈은 앱이 보낸 호실 상태(`state` 메시지)로 색과 지표를 계산합니다.

## 2. 조사 과정: 0.15초 간격 화면 기록과 배포 서버 측정

**2-1. 가짜 API로 로딩 과정을 0.15초 간격으로 기록하고, 배포 서버의 정적 파일 헤더와 API 처리 시간을 측정했습니다.**

| 확인 | 결과 |
|---|---|
| 0.15초 화면 | 트윈 `hosted` 없음, 트윈 도구 줄·지표 칩(0kW, ₩0)·층 버튼 표시 |
| 0.45초 화면 | `hosted` 적용, 트윈 자체 화면 숨김 |
| 시뮬레이션 탭 0.45초 → 0.9초 | 입력 "기간: 시간 지정, 시작, 끝" → "기간: 지금부터, 운전 시간" |
| 층 카드 | 앱 상태 기준(운전 2/16대) → 트윈 보고 기준(운전 3/26대) |
| CloudFront 응답 헤더 | `Content-Encoding` 없음, `Cache-Control` 없음 |
| API 처리 시간(배포 서버 직접 호출, 예열 후) | 19~128ms, 건물 목록 69ms, 트윈 도면 28ms |
| API 6시간 로그 | 2,268건, 중앙값 46ms, 상위 10% 292ms, 초기화 48건(평균 665ms) |

| 가설 | 판단 | 근거 |
|---|---|---|
| CloudFront가 이전 트윈 HTML을 응답 | 제외 | 배포 후 무효화 완료, 응답 파일이 새 디자인 |
| API 처리 지연 | 주원인 제외 | 예열 상태 처리 시간 128ms 이하. 3초 이상 요청은 AI 질의와 초기화 |
| 트윈 자체 화면을 먼저 표시 | 원인 | `hosted`를 첫 `state` 메시지 수신 때 적용 |

## 3. 원인: 앱 데이터 수신 전 표시·보고 순서

**3-1. 트윈은 앱의 첫 `state` 메시지를 받을 때 임베드 모드로 바꾸고, 그 전에는 자체 화면과 자체 계산값을 표시·보고했습니다.**

- 트윈은 모듈 스크립트(three.js 로드) 실행 전 HTML을 먼저 표시합니다. 이때 `hosted`가 없어 트윈 자체 도구 줄과 지표가 보였습니다.
- 첫 시뮬레이션 보고는 호실 데이터 반영 전에 보내 `hasLive`가 false였습니다. 앱은 "지금부터"를 쓸 수 없어 "시간 지정"을 표시했고, 1초 뒤 보고에서 true로 바뀌었습니다.
- 층 목록과 지표는 트윈 보고가 오면 앱 상태 기준 값을 트윈 기준 값으로 바꿨습니다. 보고 전에는 자리가 없어 보고 도착 시 지표 줄과 도구 줄이 추가되고 3D 위치가 아래로 이동했습니다.

**3-2. 지연은 압축 없는 전송과 불필요한 트윈 로드에서 발생했습니다.**

- CloudFront 동작에 `Compress`가 없어 gzip 전송을 하지 않았습니다.
- 트윈 도면이 없는 건물(본관 등 4곳)도 트윈 화면(파일 18건, 309KB)을 불러온 뒤, 트윈의 도면 요청이 실패하면 내장 3D로 바꿨습니다.
- 트윈은 데이터 파일을 하나씩 순서대로 조회했고, 앱은 트윈이 요청한 뒤에야 트윈 도면을 조회했습니다.

## 4. 해결: 첫 표시부터 임베드 모드, 데이터 수신 후 보고

**4-1. 트윈, 앱, 서버·배포를 함께 고쳤습니다(Frontend, Lambda `fix/twin-load-flicker`).**

| 위치 | 수정 |
|---|---|
| 트윈 | 주소 `host=1`이면 본문 시작 직후 `hosted` 적용. 앱 데이터 반영 후에만 보고(5초 안에 못 받으면 보고). 데이터 파일 동시 조회 |
| 앱 | 트윈 준비 신호(`twin:ready`) 때 테마·상태 재전송. 보고 전 지표 4칸·도구 줄 5칸·층 목록 자리 표시. 트윈 도면 미리 조회. 건물 목록의 `hasTwin`이 false면 트윈 화면을 불러오지 않음 |
| 서버 | 건물 목록(`GET /buildings`)에 `hasTwin` 추가 |
| 배포 | CloudFront `Compress: true`, `assets/*`는 1년 `immutable`, 그 밖은 `no-cache` |

## 5. 검증: 수정 전후 같은 조건 측정

**5-1. 수정 전(dev)과 수정 후 빌드를 같은 가짜 API와 네트워크 조건(지연 80ms, 10Mbps, API 300ms)으로 8초 동안 0.1초 간격 측정했습니다.**

| 시나리오 | 준비 시각 | 트윈 자체 화면 | 값 바뀜 |
|---|---|---|---|
| 새 건물 운영 탭 | 1.8초 → 1.4초 | 14회 → 0회 | 층 카드 2회 → 0회 |
| 새 건물 시뮬레이션 탭 | 1.6초 → 1.4초 | 15회 → 0회 | 입력 형식 1회 → 0회 |
| 본관 운영 탭 | 1.1초 → 0.7초 | 8회 → 0회 | 지표 1회 → 0회, 트윈 요청 18건 → 0건 |

- 도구 줄 자리 표시 높이는 1440, 1024, 768, 600, 520, 390px에서 실제 도구 줄과 같습니다(44, 44, 96, 96, 96, 148px).
- 새 건물의 준비 시각은 건물 목록 응답(300ms)을 받은 뒤 트윈을 불러오므로 수정 중간값(1.1초)보다 0.3초 늦습니다. 앱 안에서 건물을 옮길 때는 목록이 이미 있어 이 대기가 없습니다.
- 압축 효과는 gzip 크기 계산 값이고, 배포 후 `Content-Encoding` 헤더로 확인합니다.

## 6. 교훈: 임베드 화면은 첫 표시부터 임베드 모드

**6-1. iframe 안 화면의 모드를 부모 메시지로 바꾸면 메시지 도착 전 화면이 보입니다. 첫 표시에 필요한 모드는 주소로 전달합니다.**

보고 값을 표시하는 카드는 보고 전부터 같은 크기의 자리 표시를 배치합니다.

## 7. 같은 증상 재발 시 확인 순서

1. 트윈 iframe 주소에 `host=1`이 있는지 확인하십시오(`src/twin.ts`의 `twinSrc`).
2. 트윈 보고(`twinUi`, `sim`, `building`)가 앱 데이터 반영 전에 오는지 확인하십시오(`hostReady`).
3. 운영 사이트 응답 헤더의 `Content-Encoding`, `Cache-Control`을 확인하십시오.
4. 트윈 도면이 없는 건물에서 `digital-twin.html` 요청이 있는지 확인하십시오(건물 목록 `hasTwin`).
