# 운영 시작 0시 건물로 전력 분석 전체 400 오류

> **요약** (기준일 2026-11-21)
>
> - 시연 영상 녹화 중 판매사 화면에서 운영 시간 00~24시 건물 4개를 등록하자, 전력 분석 API가 모든 건물에서 400(`hour must be in 0..23`)을 반환했음. 약 25분(06:00경~06:25) 동안 모든 건물의 전력 분석 탭이 오류였음
> - 원인은 `energy._idle_on`이 빈 공간 운전 호실을 판정하려고 운영 시작 1시간 전 시각을 `dt.time(h0 - 1, 30)`으로 만든 것. 시작이 0시면 -1시가 됨. 이 계산은 전체 건물을 한 번에 하므로 건물 1개가 API 전체를 멈춤
> - 06:25 시연 건물 4개의 운영 시작을 01시로 바꿔 임시 복구함. 코드는 판정 시각 조회 대신 `sim.wasteful(room)`을 직접 쓰도록 수정함(Lambda #85). main `948ea9c` 배포(06:40) 후 운영 시간을 00~24시로 복원하고 전력 분석 200을 확인함
>
> | 항목 | 수정 전 | 수정 후 |
> |---|---|---|
> | 운영 시작 0시 건물이 있을 때 `/energy/compare` | 400 | 200(회귀 테스트) |
> | 영향 범위 | 등록된 건물 10곳 전체 | 없음 |
> | 운영 서버 상태 | 06:00경~06:25 오류 | 06:25 데이터 우회로 200, 06:41 운영 시작 0시 복원 후 200 |
> | 테스트 | 216개(로컬 오류 1개는 `anthropic` 미설치) | 218개(회귀 테스트 2개 추가) |
>
> **다음 작업**: 없음

## 1. 증상: 모든 건물의 전력 분석 패널에 같은 오류 문구

**1-1. 고객사 사용 장면을 녹화하던 중 에게 오피스 전력 분석 탭의 모든 패널에 `hour must be in 0..23`이 표시됐습니다.**

배경: 2026-11-21 05:58부터 판매사 관리자 계정으로 시연 영상을 녹화했습니다. 시연 기업에 건물 4개(듀플렉스 주택동 `b-m72ubbx6`, 에게 오피스 `b-8k0v3udn`, 춘천초 증축동 `b-8esweedp`, 에게 연구동 `b-znxaz0ez`)를 등록하면서, 녹화 시각에도 냉난방이 운전되도록 운영 시간을 00~24시로 저장했습니다. 건물 정보 화면은 운영 시작 00시를 선택지로 제공하고, 서버(`admin.py`)도 0~24 정수를 허용합니다.

전력 분석 탭은 `/energy/compare`(건물 비교), `/energy/trend`(기간 추이), `/energy/heatmap`(요일×시간), 사용 구성 API를 조회합니다. 06:22 녹화에서 네 패널이 모두 같은 오류 문구를 표시했습니다.

## 2. 조사 난점: 서버 오류가 잘못된 요청(400)으로 보임

**2-1. 응답 코드가 400이라 처음에는 화면이 잘못된 인자를 보낸 것처럼 보였습니다.**

`energy.handler`는 잘못된 `building`, `period`, `weeks`를 알리려고 `ValueError`를 모두 400으로 바꿉니다. 내부 계산에서 생긴 `ValueError`도 같은 경로로 400이 되어, 서버 결함이 요청 오류로 표시됐습니다.

## 3. 조사 과정: 영향 범위, 건물 설정, 코드

**3-1. 다른 건물의 전력 분석도 같은 오류여서 시연 건물만의 문제가 아니었습니다.**

| 확인(06:23, 판매사 토큰으로 조회) | 결과 |
|---|---|
| `GET /energy/compare?period=day` | 400 `hour must be in 0..23` |
| `GET /energy/heatmap?building=b-6osl4hmx`(디아크 문화관) | 400 같은 문구 |
| `GET /energy/trend?building=b-6osl4hmx&period=day` | 400 같은 문구 |
| `GET /buildings` 운영 시간 | 시연 건물 4개 `[0, 24]`, ifc건물 `[2, 24]`, 나머지 `[8, 21]` |

**3-2. 운영 시간 값이 시각 계산에 들어가는 곳을 찾아 가설을 좁혔습니다.**

| 가설 | 판단 | 근거 |
|---|---|---|
| 화면이 잘못된 시각 인자를 보냄 | 제외 | 인자가 없는 `/energy/compare`도 같은 오류 |
| 운영 종료 24시가 원인 | 제외 | ifc건물 `[2, 24]`는 이전부터 있었고 오류 없음 |
| 운영 시작 0시에서 -1시 계산 | 채택 | `energy._idle_on`의 `dt.time(h0 - 1, 30)`. 시작 0시면 `hour=-1` |
| 다른 모듈의 같은 계산 | 제외 | `recommend.py`, `sim.py`, `usage.py`, `history.py`는 0~23 범위 비교만 사용 |

## 4. 원인: 판정 시각 조회와 전체 건물 일괄 계산

**4-1. 빈 공간 운전 호실 판정이 운영 시작 1시간 전 시각을 만들었고, 그 계산을 전체 건물에 대해 한 번에 했습니다.**

- `energy._idle_on(room)`은 "재실 0명이어도 운전하는 호실"을 찾으려고 운영 시작 1시간 전 30분(`dt.time(h0 - 1, 30)`)의 `sim.state`를 조회했습니다. 그 시각은 재실 0명이라 운전 여부가 곧 빈 공간 운전 여부입니다.
- 운영 시작이 0시면 `dt.time(-1, 30)`이 `ValueError`를 냅니다.
- `energy._meta(version)`은 `buildings.LIST`의 모든 건물, 모든 호실에 대해 `_idle_on`을 계산해 캐시합니다. 따라서 운영 시작 0시 건물이 1개만 있어도 모든 전력 분석 요청이 실패합니다.

## 5. 해결: 데이터 우회 후 판정 함수 직접 사용

**5-1. 운영 서버는 시연 건물의 운영 시작을 바꿔 복구했고, 코드는 판정을 시각 조회 없이 하도록 수정했습니다.**

| 단계 | 내용 |
|---|---|
| 임시 복구(06:25) | 판매사 관리자 API `PATCH /admin/buildings/{id}`로 시연 건물 4개의 운영 시간을 `[1, 24]`로 변경. 5초 뒤 전체 전력 분석 API 200 확인 |
| 코드 수정(Lambda #85, dev `4333df5`) | `sim.wasteful(room)` 추가(`sim.state`의 빈 공간 운전 판정과 같은 식). `_idle_on`은 `sim.wasteful`로 판정하고 운전 시간 범위를 `max(h0 - 1, 0)`~`min(h1 + 3, 24)`로 제한. 사용하지 않는 `_PROBE` 삭제 |
| 배포(06:40) | Lambda main `948ea9c`(PR #87, #85와 #86 포함)를 `maestro` 스택에 배포. API 함수 배포 코드의 `energy.py`가 main과 같은 것을 확인 |
| 운영 시간 복원(06:41) | 시연 건물 4개를 `[0, 24]`로 복원 |
| 회귀 테스트 | `MidnightStartTest` 2개: 운영 시작 0시 호실의 정지 생략 규칙이 `sim.state`와 같은지, 운영 시작 0시 건물이 있어도 `/energy/compare`가 200인지 |

## 6. 검증: 수정 전 실패 재현과 수정 후 통과

**6-1. 회귀 테스트는 수정 전 코드에서 운영 서버와 같은 문구로 실패했고, 수정 후 통과했습니다.**

| 확인 | 결과 |
|---|---|
| 수정 전 `MidnightStartTest` | 실패 1, 오류 1. `400 != 200 : {'error': 'hour must be in 0..23, not -1'}` |
| 수정 후 `python3 -m unittest tests.test_energy` | 15개 통과 |
| 수정 후 `python3 -m unittest discover tests` | 218개 중 오류 1개(`test_answer_format`, 로컬 `anthropic` 미설치). 수정 전 dev에서도 같은 오류 |
| 운영 서버(데이터 우회 후) | `/energy/compare`, 디아크 문화관·에게 오피스 `/energy/heatmap` 200 |
| 운영 서버(배포 후, 운영 시작 0시 건물 4개) | `/energy/compare`, 디아크 문화관·에게 오피스 `/energy/heatmap`, 에게 오피스 `/energy/trend` 200 |

주: 06:25~06:40에는 수정 코드가 배포 전이라 운영 시작 0시 건물을 등록하면 같은 오류가 날 수 있었습니다. 06:40 배포 후에는 해당하지 않습니다.

## 7. 교훈: 화면이 허용하는 경계값과 일괄 계산

**7-1. 화면과 API가 허용하는 경계값(0시 시작)을 계산 코드도 처리하는지 테스트로 확인해야 합니다.**

- 운영 시간 입력은 0~24를 허용했지만, 계산 코드는 시작 1시간 전이 항상 있다고 가정했습니다.
- 전체 건물을 한 번에 계산하는 캐시는 건물 1개의 오류를 전체 장애로 키웁니다. 건물 단위 오류 격리는 별도 과제로 남깁니다.
- 내부 `ValueError`를 400으로 바꾸는 처리는 서버 결함을 요청 오류처럼 보이게 합니다.

## 8. 같은 증상 재발 시 확인 순서

**8-1. 전력 분석이 전체 건물에서 같은 400 문구를 내면 최근 바뀐 건물 설정부터 확인하십시오.**

1. 다른 건물의 `/energy/compare`, `/energy/heatmap`도 같은 오류인지 확인하십시오. 전체 오류면 일괄 계산(`_meta`) 단계 문제입니다.
2. `GET /buildings`의 `hours`, `weekend`에서 최근 등록·수정한 건물의 경계값(0시 시작, 24시 종료)을 확인하십시오.
3. 오류 문구로 `energy.py`, `sim.py`의 시각 생성(`dt.time`, `replace(hour=...)`)을 찾고, 해당 값으로 `tests/test_energy.py`에 회귀 테스트를 추가하십시오.
4. 급하게 복구해야 하면 해당 건물의 운영 시간을 판매사 화면 '정보 수정'으로 경계값 밖으로 바꾸십시오.
